# Spec P8.1 — 会话挂钩 + 统一异步任务

| 字段 | 值 |
|---|---|
| ID | P8.1 |
| 状态 | in_progress（P81-01–18 测例绿；仅 P81-17 真机 `next` 当步生效待补） |
| 依赖 | P4.2 A（三工具 + host）；P7.3 `appendSessionTurns` / `endSession`；P6.3 `compileSession`；P6.5 `shouldQueryMemory` |
| 对应架构 | P4.2 §9（B 档，**实现迁入本期**）；TODO #1 + #2 |
| 仓库 | 并列仓 `dsh-df-memory/`（主）；本仓仅当 job 类型需导出时加薄类型，**不**把 Cordis 拉进 core |

> 承接 P4.2 B：产品要每轮 user/assistant 进 inbox。七期只交付了 CLI `--buffer`。  
> 同时修 UX：`memory_remember` 同步 compile 实测 15–18s，必须「接受 → 后台执行 → 状态可查」。  
> **#1 与 #2 共用一套任务机制**，禁止两套异步。

## 1. 目标

1. DSH 会话按下列范式挂钩（`autoBuffer` **默认 true**）：

```
session-start          → 惰性：首条文本轮再开 inbox session
每轮 user/assistant    → appendSessionTurns（同步、只存文本）
窗口满                 → 入队 compile（异步）
会话结束 / 插件卸载    → 入队 endSession（剩余 turns）
pre-step               → shouldQueryMemory；命中则 hybridQuery + agent.inject(top-k)
```

2. `memory_remember` 默认入队，立即返回 `{ accepted: true, task_id, session_id, status: "pending" }`；最终 `kept/dropped/distill` 只出现在 status 查询。  
3. 窗口 flush、`endSession`、显式 remember **同一 JobRunner**。  
4. 挂钩层**主动丢弃** `role=tool` 与 `system`（以及工具调用块）；不得依赖 `archiveSession` 的 `toolMaxChars` 截断。  
5. 失败可观测、fail-open：任务 `failed` 时 inbox 标 `failed`（P6.2），**不写 L0**，不留下半成品 md。  
6. 同仓并发 remember / flush 复用 **同一个** `WriteQueue` 实例（host 缓存键已含 `repoRoot`+`brainId`）。

## 2. 非目标

- 改 CLI `remember` 默认同步（P6.4 保持）  
- 守护进程 / Idle TTL / PreCompact  
- fire-and-forget（无 task_id、不可查）  
- 把 DSH transcript / 工具结果 dump 进 `sources/`  
- 在未确认 DSH jobs 契约前，把任务权威放到宿主 jobs 服务  
- 改 P4.2 A 的无 Key 合同（仍 `E_DISABLED`，不写 L0）  
- 实现 P8.3 的 skill 注入（本 Spec 只做知识层 `shouldQueryMemory` inject）

**调研补充（写实现时有用）**：

- 备选挂钩点：`agent/inbox/inserted` / `agent/inbox/claimed` / `agent/inbox/discarded`（`dsh-agent`，payload `{ agent, message: UserMessage, turn? }`）——claimed 的消息即将进 step，与 pre-step 时序接近；若 waterfall 改造面大，可退化用 claimed + 注入时序需真机验证。
- `agent/created` / `agent/status`（`idle ⇄ running`）：生命周期观测，不用作记忆挂钩。
- `user/message` 来源由 `source.kind` 区分：人类 = `user`，模型侧 user 形消息 = `model`（**进记忆、不截断**），`agent.inject` = `plugin`（不进），goal 续轮 = `goal`（不进）。见 §3.1 #5。
- `assistant/message` 与 `tool/call` 是分离事件：assistant 只拼 `{type:'text', text}` 块，**不按 `toolMaxChars` 截断**。

**jobs 选型结论**（§4.3 适配面）：

实测 `ctx.get("jobs")`（`dsh-jobs` `JobRegistry`）契约与 §4.3 假定**不符**：无 `enqueue(name, payload)`；真实面是 `start(spec: { kind, label, outputLimitBytes?, owner?: Agent, run(): JobHooks }) → JobId`（id 形如 `<kind>-N`）+ `get(id, caller?)` / `read` / `list` / `kill` / `wait` / `onJobDone` / `onJobsChanged` / `attachController`；`kind` 需声明合并进 `JobKindMap`。

**选型结论（写进插件 README 一行）**：`ctx.get("jobs")` 无 enqueue 契约，**按 §4.2 `.dfmemory/jobs/` 文件队列为权威**；宿主适配面若要委托，映射到 `JobRegistry.start`（kind 扩展 `'df-memory'`，结果经 `JobHooks.done` 回传），job 文件仍作镜像。不阻塞文件队列实现。

## 4. 技术方案

### 4.1 挂钩过滤

```
onTurn(raw):
  if event.type == user/message && source.kind not in {user, model}: drop
  if event.type == assistant/message: keep（全文）
  if event.type in {tool/call, tool/result, assistant/chunk, …}: drop
  if 空文本: drop
  text = content 中 text 块完整拼接（assistant / kind=model 禁止截断）
  role = user/message → user；assistant/message → assistant
  appendSessionTurns({ turns: [{ role, text, at? }], window: true })
  if result.compiled || result.shouldCompile: enqueue({ kind: "compile", session_id })
```

`appendSessionTurns` 已按 P7.3 在达 `window_max_turns` / `window_max_chars` 时 compile。挂钩层若走「先 append 再自己入队」，必须保证 **不会 compile 两次**：

- **锁定**：挂钩只调用 `appendSessionTurns` / `endSession` 的 **enqueue 包装**（见 §4.4），不直接调会同步 `complete()` 的入口。  
- 包装内：达窗或 `end` → 只入队，不在请求线程里跑 LLM。

core 若当前 `appendSessionTurns` 在达窗时同步 `compileSession`，本仓加一个显式选项或新函数：

```ts
appendSessionTurns(opts & { deferCompile?: boolean }): Promise<AppendResult>
// deferCompile=true：达窗时返回 { shouldCompile: true, session_id }，不调 complete()
```

这是本期 **唯一允许的 core 行为增量**（P81-01）。默认 `deferCompile` 缺省 = `false`，CLI `--buffer` 行为不变。

### 4.2 Job 文件（权威）

```
.dfmemory/jobs/{brainId}/{task_id}.json
```

gitignore：在仓模板 / 插件 README 写明忽略 `.dfmemory/jobs/`（与 inbox 同级，非 L0、不进检索、不进 git）。

```ts
type MemoryJob = {
  task_id: string;            // ulid 或 uuid
  kind: "compile" | "end_session" | "remember";
  status: "pending" | "running" | "done" | "failed";
  brain_id: string;
  session_id: string;
  accepted_at: string;        // ISO
  started_at?: string;
  finished_at?: string;
  result?: {
    kept: number;
    dropped: number;
    errors: unknown[];
    distill?: { written?: number; skipped_reason?: string };
  };
  error?: { code: string; message: string };
};
```

- 入队：写 `pending` 文件后返回 `task_id`。  
- 执行：CAS `pending → running`；跑 `compileSession` / `endSession`（`endSession` 内部仍是 compile 剩余）。  
- 成功：`done` + `result`。  
- 失败：`failed` + `error`（`E_DISABLED` / `E_LLM` / `E_VALIDATION` / `E_TIMEOUT` …）；inbox 已有语义保持。  
- 超时：`compile.job_timeout_ms` 默认 **120000**；超时标 `failed` + `E_TIMEOUT`，不写 L0。  
- 保留：同一 brain 最多 **50** 条或 **7 天**（先到先删 `done/failed`）；`pending/running` 不删。  
- **禁止**任务失败后留下 `brains/**` 半成品（compile 仍是一场一次 `WriteQueue.execute`）。

新增错误码（CLI/工具共用字符串，写入 `00-conventions` 表）：

| 码 | 含义 |
|---|---|
| `E_TIMEOUT` | 任务超过 `job_timeout_ms` |
| `E_JOB` | 任务文件损坏 / 状态非法 / 找不到 task_id |

### 4.3 可选宿主 jobs 适配面

> 实测结论（§3）：`JobRegistry` **无** `enqueue`；真实面为 `start(spec)`。委托面按下列形状（duck-type，`kind` 声明合并进 `JobKindMap` 扩展 `'df-memory'`）：

```ts
{
  start(spec: { kind: string; label: string; owner?: unknown; run(): { cancel(r?: string): void; done: Promise<{ status: 'completed'|'killed'|'failed'; detail?: string; output?: string }>; readOutput?(): string } }): { id: string }
  get(id: string, caller?: unknown): { status: string; detail?: string; output?: string } | null
}
```

委托时 **仍写** §4.2 文件作镜像（或 job 文件里记 `host_job_id`）。查 status 以能返回 §4.2 形状为准。宿主不可用则静默回退文件队列，不报错。**选型结论一行（插件 README）**：宿主 jobs 无 enqueue 契约 → 以 §4.2 文件队列为权威；适配 `start` 仅在契约核验通过后启用。

### 4.4 JobRunner 与 WriteQueue

```
HostCache key = repoRoot + brainId
  → 一个 WriteQueue
  → 一个 JobRunner（串行执行该 brain 的 compile 类任务）
```

同一 brain 多个 remember **排队**，不并行 compile（避免 inbox `.open` 与写锁竞态）。不同 brain 可以各有 runner。

卸载：`host.close()` 先 `enqueue endSession` 并 **best-effort 等当前 running 结束**（上限 `job_timeout_ms`），再关 PGLite。等不及 → 当前 job 标 failed；pending 留盘，下次 `apply` 可 `inbox retry`（P7.5）或 runner 启动时扫描 `pending`。

启动扫描：host 首次加载（`apply` 后第一次工具 / 挂钩调用）时扫描该 brain 下 `pending`/`running`（崩溃残留的 `running` 视为失败并改 `failed` + `E_JOB`，turns 仍在 inbox，可 retry）；新任务入队时也会再扫一次（幂等）。

### 4.5 `memory_remember` 契约变更（相对 P4.2 A）

| 参数 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `body` | string | 必填 | 原文（一场 user 文本，或模型主动记的一段） |
| `wait` | boolean | `false`（八期插件） | `true` = 同步等到 done/failed（A 兼容 / 调试） |

成功（异步，立即）：

```json
{ "accepted": true, "task_id": "…", "session_id": "…", "status": "pending" }
```

成功（`wait: true` 且完成）：保持 A 的 `session_id` / `kept` / `dropped` / `errors`，并加 `task_id`、`status: "done"`。  
无 Key：异步任务也会 `failed` + `E_DISABLED`；`wait: true` 立即返回该错误。**不写 L0**。

新工具 `memory_job_status`：

| 参数 | 映射 |
|---|---|
| `task_id: string` | 读 job 文件 |

返回整份 `MemoryJob`。找不到 → `E_JOB` 或 `E_NOT_FOUND`。

不强制新开 `memory_remember_status` 别名。prompt section 必须写：remember 先返回 accepted；查结果用 `memory_job_status`。

### 4.7 知识层注入（B 档另一半）

`pre-step`（或对等事件）：

1. `shouldQueryMemory(userText, ctx)`  
2. 未命中 → 不检索  
3. 命中 → `hybridQuery` top-k（k 默认 5，可配 `injectTopK`）  
4. 按 §3.1 #4：优先 `next({ …payload, messages: […, injected] })`；失败才 `agent.inject`。注入体是 hits 摘要（path/title/snippet/schema_type），**不是**整篇 L0；`source.kind` 必须是 `plugin`  
5. 检索失败 fail-open：不注入、不抛到宿主；不改 `next` 的 messages

本步 **同步**（无 LLM）。P8.2 落地后 hits 带层标注；本期可用现有 hit 形状。
