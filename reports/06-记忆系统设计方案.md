# 团队记忆系统设计方案（df-memory）

> 基于对 GBrain、Mem0、MemOS、OpenViking 四个项目的深度调研（见 `01`~`05` 报告），集成各项目之长，为你们的平台（团队空间、沙箱执行 agent、issue 驱动任务、共享 session）设计一套通用团队记忆系统。
> 设计定位：**通用架构设计**，可落地为平台功能模块；已结合 df-app 架构蓝图（Java 17 / MySQL / Kafka / Thrift / workspace 体系）。
> 日期：2026-08-02 ｜ 语言：中文

---

## 一、设计目标与原则

### 1.1 要解决的核心问题

你们的平台是"issue 驱动的协作编码平台"：用户创建工作项 → 云沙箱中 Coding Agent 执行 → 过程中产生海量消息、计划、产物。当前的痛点与四项目调研揭示的记忆通病一致：

1. **经验不沉淀**：Agent 每轮任务完成后，方案、踩坑、产物、决策依据都散落在会话里，下个任务从零开始；
2. **知识不共享**：团队成员/不同 Agent 之间不共享"这个项目该怎么弄"的上下文；
3. **复用无飞轮**：做过的同类 issue 不能成为下个 issue 的输入；
4. **上下文成本**：每次检索把整段历史塞进 prompt，token 成本高且相关性差。

### 1.2 设计目标

1. **让每个 issue 成为一条记忆主干**：围绕 issue 沉淀需求、决策、方案、产物、经验，形成可寻址、可检索、可演化的记忆树；
2. **让记忆自我维护**：去重、纠错、浓缩、矛盾检测自动进行（GBrain dream cycle 理念）；
3. **让经验成为飞轮**：完成的任务提炼为可复用经验，同类任务自动注入（OpenViking/MemOS 实证）；
4. **让成本、隔离、可观测成为一等公民**。

### 1.3 设计原则（四项目精华的提炼）

| 原则 | 来源借鉴 | 含义 |
|---|---|---|
| **记忆 = 文档树 + 知识图谱** | OpenViking + GBrain | 确定性路径可寻址（`viking://` 式）+ typed edges 关系推理（零 LLM） |
| **写入只增不覆盖（ADD-only 变体）** | Mem0 | 提取单遍、历史保留，更新语义由 merge_op + 检索排序承载 |
| **写入时分层，读取时按需** | OpenViking | L0 摘要/L1 概览/L2 全文，写入管线异步生成，检索按层注入 |
| **零 LLM 也能跑，LLM 只用于富化** | GBrain | 链接、意图、关系解析用确定性正则；LLM 用于提取/综合/维护 |
| **异步写入 + 审计 + 可观测** | MemOS + OpenViking | 写入不阻塞主链路，memory_diff 变更审计，explain 分数可查 |
| **成本是第一等公民** | GBrain | search mode 档位 + cost cap + 熔断器 |
| **多租户隔离由存储层强制** | GBrain + OpenViking | 不是 UI 隐藏，而是 SQL/存储层架构保证 |

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────────────┐
```

### 2.2 独立项目定位与 df-app 的关系（D10/D11/D12）

- **服务形态**：`df-memory` 是**独立项目**——独立仓库、独立部署（Docker/独立进程）、**独立 MySQL 库（`df_memory`）**。内部沿用 df-app 四层工程规范（代码习惯一致），但**不依赖 df-app 任何代码/配置中心/调度**。
- **对外接口**：df-memory 对外暴露 REST（`/api/**`）+ MCP，df-app 作为**调用方**接入：df 后端直连（带 API Token）、前端经 df-gateway 反向代理 `/memory/**`、沙箱 agent 连 MCP server（D12）。
- **摄取边界**：df-memory **直接只读 df-app 库**（专用只读账号 + 增量游标）——`chat_message_log`（消息流）、`work_artifact`（产物）、`work_phase`（阶段推进）。理由：DB 的 `entry_index` 是**唯一有序真源**，规避 Kafka 乱序/丢序风险（D6）。
- **与现有 workspace_memory 表的关系**：df-memory 不读它；迁移由 df-app 侧按需执行，避免双份存储。
- **与现有 OpenViking 集成的取舍**：蓝图将 OpenViking 列为"可裁剪"记忆。本设计给出两条路：
  - **方案 A（推荐，自建）**：按本文档自建 df-memory（独立项目），向量后端可插拔（Qdrant/Milvus），彻底掌控数据与成本；
  - **方案 B（借壳）**：复用 OpenViking 作为存储与检索后端，df-memory 只做上层业务编排。代价是 AGPL 合规风险（网络服务需开源）与火山生态绑定，不推荐用于商用核心。

### 2.3 组件划分（单一职责，可独立测试）

| 组件 | 职责 | 依赖 |
|---|---|---|
| `ingest` | **只读 df-app 库**，增量摄取消息/产物/阶段事件 | df-app 库（只读账号）、自有库 |
| `extract` | LLM 单遍 ADD-only 提取事实/实体；schema 驱动 | LLM、schema registry |
| `layer` | L0/L1/L2 分层摘要生成（异步） | LLM、Vector store |
| `graph` | 零 LLM 正则建 typed edges；关系查询 arm | 自有 MySQL |
| `dedup` | cosine 快路径 + LLM 降级 + merge_op 合并 | Vector store、LLM |
| `retrieve` | 意图分类 + 混合召回 + RRF + 分层重排 + rerank | Vector、自有 MySQL、LLM |
| `experience` | issue 完成后经验提炼（trajectory→skill） | LLM、extract |
| `maintain` | 夜间维护循环（去重/纠错/浓缩/矛盾检测） | 全组件 |
| `admin` | 权限（API Token）、配置、成本控制、审计查询 | 自有 MySQL |

## 三、核心概念与数据模型

### 3.1 双组织模型：文档树 × 知识图谱

**（1）可寻址文档树（取 OpenViking）**

每个工作项（issue）在记忆库里是一棵确定性路径的子树：

```
mem://{workspace_id}/
├── projects/{repoKey}/                  # 项目级共享知识
│   ├── .abstract  .overview            # L0/L1 分层
│   └── docs/  decisions/  patterns/
├── issues/{issue_id}/                   # 每 issue 一条记忆主干
│   ├── .abstract  .overview
│   ├── requirement.md                   # 需求（来自 work_item.content）
│   ├── decisions/{n}-{title}.md         # 决策记录（何时/谁/为什么/备选）
│   ├── plans/                           # 方案（来自 work_artifact PLAN）
│   ├── tests/                           # 测试报告（来自 work_artifact TEST）
│   ├── lessons.md                       # 踩坑/经验（session 提炼）
│   └── sessions/{session_id}/           # 会话原始记忆
├── members/{user_id}/                   # 成员级记忆（偏好/专长）
└── .global/                             # 团队级全局知识
```

路径是**确定性寻址**：`mem://{ws}/issues/{id}/decisions/1` 即某决策文档，可用 `ls/tree/find` 浏览。目录/节点各自带 `.abstract`(L0) / `.overview`(L1)，供检索预筛与按需加载。

**（2）知识图谱（取 GBrain 零 LLM 边）**

文档树之上叠加 typed edges，让"谁在做什么""这个 issue 用了什么方案"这类**关系查询**可确定性回答，不依赖 embedding：

```
issue#123 ──belongs_to──> project:df-app
issue#123 ──decided──> decisions/2:用方案B
issue#123 ──produced_by──> agent:claude
user:alice ──works_on──> issue#123
issue#124 ──references──> issue#123        （同场景复用的自然涌现）
```

**边全部由零 LLM 正则规则生成**（GBrain `inferLinkType` 模式）：从 markdown 链接、动词模式（`founded/decided/works_on/references`）、mention 抽取。写文档时自动建图，图免费增长。

### 3.2 记忆类型（schema 驱动，取 OpenViking YAML schema）

每种记忆类型由 schema 定义（字段、merge_op、embedding 模板、文件名模板），可扩展：

| schema | 对应节点 | 核心字段 | merge_op |
|---|---|---|---|
| `requirement` | issues/{id}/requirement | content, source(issue) | immutable |
| `decision` | issues/{id}/decisions/* | title, context, decision, alternatives, author, date | patch |
| `lesson` | issues/{id}/lessons | problem, cause, fix, applicable_to | append |
| `experience` | issues/{id}/experience | trigger, procedure, boundary, result | append |
| `member_profile` | members/{id}/profile | role, specialties, preferences | patch |
| `session` | issues/{id}/sessions/* | 会话摘要, agent, outcome | immutable |
| `skill` | .global/skills/* | name, prompt, examples, counter_examples | patch |

### 3.3 核心表（MySQL，对齐 df-app 现有规范）

> 与现有表（work_item/work_phase/work_artifact/chat_message_log）逻辑关联，均带 `workspace_id` 前缀强制隔离。

```sql
-- 记忆节点（文档树）：可寻址 + 分层
mem_node: id PK; workspace_id; node_id; node_type; path VARCHAR; -- 确定性路径
  parent_id; schema_type;
  abstract_text LONGTEXT; -- L0
  overview_text LONGTEXT; -- L1
  content LONGTEXT;       -- L2 全文
  version INT; status TINYINT; -- active/archived
  source_ref VARCHAR;     -- 关联 work_item/session/artifact
  created_by; agent_id; created_at; updated_at;
  UNIQUE KEY(workspace_id, path)

-- 图谱边（零 LLM 生成）
mem_edge: id PK; workspace_id; from_node VARCHAR; to_node VARCHAR;
  link_type VARCHAR;      -- decided/produced_by/works_on/references/...
  link_source VARCHAR;    -- markdown/wiki/ner/mention
  link_kind VARCHAR;      -- plain/typed_ner
  UNIQUE KEY(workspace_id, from_node, to_node, link_type, link_source)

-- 原子事实（ADD-only，向量检索主对象）
mem_fact: id PK; workspace_id; scope VARCHAR; -- issue/session/user/global
  scope_id VARCHAR; text TEXT; text_hash CHAR(32);
  embedding JSON;          -- 向量（或存向量库由 id 关联）
  attributed_to VARCHAR; user_id; agent_id; issue_id; session_id;
  event_type VARCHAR;      -- meeting/decision/job_change/...
  status TINYINT;          -- active/expired/archived
  created_at; updated_at;
  UNIQUE KEY(workspace_id, text_hash)

-- 实体 + 链接（Mem0 式轻量图记忆，可选降级）
mem_entity: id PK; workspace_id; entity_type VARCHAR; -- PROPER/TOPIC/IDENTIFIER/QUOTED
  entity_text TEXT; normalized_text TEXT;
  linked_fact_ids JSON; created_at; updated_at

-- 变更审计（memory_diff）
mem_change_log: id PK; workspace_id; ref_id VARCHAR; ref_type VARCHAR;
  action VARCHAR;          -- add/update/delete/merge
  before_text TEXT; after_text TEXT; actor VARCHAR; -- user_id/agent_id
  trace_id VARCHAR; created_at

-- 经验/技能结晶
mem_experience: id PK; workspace_id; issue_id; trigger_text TEXT;
  procedure_json TEXT; applicability TEXT; result_json TEXT;
  source_trajectory_ids JSON; status TINYINT; eta_score DECIMAL; -- 复用度
  created_at; updated_at
```

## 四、写入管线（Ingestion Pipeline）

### 4.1 多源摄取

| 源 | 触发 | 落到 |
|---|---|---|
| `chat_message_log`（会话消息） | Kafka consumer | session 节点 + 提取事实 |
| `work_artifact`（PLAN/TEST/PREVIEW_URL） | 消息旁路已落地，df-memory 读表 | plans/tests 节点 |
| `work_phase` 推进 | 阶段事件 | 记忆树路径节点 + 图谱边 |
| 用户/Agent 手动写入 | REST/MCP `remember` | 任意路径节点 |
| issue 完成（pr_merged/deployed） | 阶段事件 | 触发 experience 提炼 |

### 4.2 提取（取 Mem0 ADD-only + GBrain 快路径）

```
消息流 → 分组(按 issue/session)
  → [快路径] 已有相似事实? cosine ≥ 0.95 → 跳过（零 LLM）
  → LLM 单遍提取（ADD-only，一次调用只做新增）
      prompt 规格（Mem0 式"prompt 即规格"）：
        - 只提取有证据的独立事实
        - 相对时间锚定 Observation Date
        - 归因：user 消息→user_id，agent 消息→agent_id
        - 输出 15-80 词自包含事实 + 实体 + 关联记忆
  → 批量嵌入 → MD5 去重 → 批量入库 → 实体链接
  → 异步生成 L0/L1 分层（OpenViking）
  → 零 LLM 建边（GBrain）
  → 写 memory_diff 审计
```

**关键取舍**：
- **写入异步化**：所有摄取走队列，`remember` API 立即返回，提取在后台完成（MemOS/OpenViking 模式），不阻塞用户主流程。
- **事实与文档并存**：`mem_fact` 承载原子事实（向量检索对象），`mem_node` 承载组织化文档（路径寻址对象），两者通过 `mem_edge` 关联。检索两个通道都要。
- **提取质量**：`prompt` 作为一等代码资产版本管理（Mem0 理念）；失败逐条回退，LLM 不可用降级为原样存储（`infer=False` 语义）。

### 4.3 分层生成（取 OpenViking L0/L1/L2）

- **L0 `.abstract`**（~100 token）：单句摘要，向量检索与快速过滤用；
- **L1 `.overview`**（~1-2k token）：结构 + 要点，rerank 与导航用；
- **L2 全文**：原始内容，按需加载。

生成顺序自底向上（Leaf → Parent → Root），子目录 L0 聚合进父目录 L1。**读取时按需取层**，这是省 token 的关键（OpenViking 实证 -91%）。

## 五、检索管线（Retrieval Pipeline）

### 5.1 完整链路

```
Query（来自聊天 / 前端 / MCP find）
  → 意图分类（零 LLM 正则：issue查询/经验查询/人物查询/一般查询）
  → 混合召回（并行）：
      ① 语义检索（向量，over-fetch max(limit*4,60)）
      ② BM25 关键词（MySQL fulltext 或词法索引）
      ③ 图谱边遍历（关系查询 arm：谁/哪个issue/什么方案）
      ④ 实体链接 boost（mem_entity → 关联事实）
  → RRF 融合（GBrain k=60）+ 归一化（Mem0 自适应 sigmoid）
  → 目录级预筛（OpenViking：优先定位高分目录子树）
  → 分层加载（只取 L0/L1 判断相关性，命中才取 L2）
  → 可选 reranker（tokenmax 档）
  → explain 分数 + create_safety 返回
```

### 5.2 团队场景的三类典型查询

| 场景 | 查询 | 走哪条通道 |
|---|---|---|
| **复用**："类似 '支付网关重构' 的任务我们做过吗？怎么做的？" | 经验查询 | 语义 + 图谱 reference 边 + 目录预筛 |
| **上下文**："issue#123 当前方案是什么？谁决定的？" | issue 查询 | 确定性路径直达 + 图谱 decided/works_on |
| **人**："Alice 在哪些 issue 上做过后端？" | 人物查询 | 图谱 works_on + 语义 |

### 5.3 检索可观测（Mem0 explain + OpenViking 轨迹）

- 每个结果带 `evidence`（exact_path/alias/semantic/keyword/graph）+ `score_details`（各信号分/分母/阈值）；
- 记录检索 `searched_directories` 与 query_plan，`df-memory observer` 查看整体指标（zero-result rate / avg score / latency / rerank 使用率）。

## 六、记忆演化与飞轮

### 6.1 维护循环（取 GBrain dream cycle，夜间/空闲 cron）

```
maintain（每晚或低峰）：
  ① lint：路径/引用完整性
  ② dedup：重复节点合并，未落地 L0/L1 补生成
  ③ consolidate：相关事实 → 浓缩为"综合观点"（mem_node 的 .overview 升华）
  ④ contradiction：矛盾检测（两个决策文档冲突 → 标记待人工裁决）
  ⑤ stale：过期事实归档（按活跃度/最后引用时间）
  ⑥ embed --stale：未向量化的补齐
```

### 6.2 经验提炼（取 MemOS Reflect2Evolve + OpenViking experience memory）

issue 完成后（pr_merged/deployed 阶段事件）触发：

```
issue 完成 → 收集轨迹（sessions + decisions + lessons + 产物）
  → 提炼：触发条件(trigger) / 解决过程(procedure) / 适用边界(boundary) / 结果(result)
  → 去重判定：与现有 mem_experience 查重（LLM）
  → 写入 mem_experience + 图谱 reference 边
  → （高级）重复 N 次的 pattern 结晶为可调用 Skill（team skill 库）
```

**飞轮闭环**：

```
issue 创建
  → 检索注入历史经验（"类似任务怎么做"）→ 少踩坑、更高效
  → Agent 执行，产物/决策/教训沉淀进记忆树
  → issue 完成 → 提炼经验 → 图谱新增 reference 边
  → 下一个同类 issue 创建 → 命中复用 → 循环加速
```

这是整个设计最核心的"飞轮"：**做过的任务成为下个任务的输入**，且随着 issue 增多，经验密度上升、重复工作下降。OpenViking tau2 实证：经验记忆提升任务成功率 +6.87~+11.87pp。

### 6.3 反馈修正（取 MemOS MemFeedback）

用户/Agent 可用自然语言修正记忆："decision/2 里其实选了方案 C，帮我改"。走 `update` 管线 + merge_op 语义合并 + memory_diff 审计，不覆盖历史。

## 七、多租户与权限（对齐 df-app）

### 7.1 三层身份模型

| 层 | 对应 df-app | 隔离粒度 |
|---|---|---|
| **workspace**（租户） | workspace_id | 完全隔离，所有表带前缀 |
| **user**（成员） | 用户 | issue/成员级记忆 |
| **agent**（执行者） | agent（claude/cursor/...） | 归因 + 隔离 |

### 7.2 隔离由存储层强制（取 GBrain SQL 层 + OpenViking 前缀）

- 所有表 `workspace_id` 参与主键/唯一键，DAO 层 `@MdpMySQLReadMaster` 读取时强制注入 workspace 过滤（GBrain `sourceScopeOpts` 模式，禁止手写过滤）；
- **agent 只能读写自己参与的 issue 记忆**（df-app 的 session ownership 语义可复用）；用户跨 workspace 访问一律拒绝；
- 集成现有 SSO：df-memory 信任 df-gateway 注入的身份头，不做自建认证（复用 df-app 换票体系）。

### 7.3 记忆可见性

| 记忆 | 可见范围 |
|---|---|
| `mem://{ws}/projects/` | workspace 内全部成员 |
| `mem://{ws}/issues/{id}/` | 该 issue 参与成员 + 关联 agent |
| `mem://{ws}/members/{id}/` | 本人 + workspace 管理员 |
| `.global/` 团队经验/技能 | workspace 内全部成员（团队复用飞轮的载体） |

## 八、可观测性、审计与成本控制

### 8.1 审计（取 OpenViking memory_diff + Mem0 history）

- 每次变更写 `mem_change_log`（action/before/after/actor/trace_id），可回滚可追溯——团队共享记忆的底线；
- 复用 df-app 已有 trace_id 贯穿全链路。

### 8.2 成本控制（取 GBrain 成本一等公民）

| 机制 | 说明 |
|---|---|
| **search mode 档位** | conservative（无 LLM 检索，纯混合）/ balanced（默认）/ tokenmax（+扩写 +rerank），档位化成本/质量 |
| **cost cap + 预览** | 大规模操作前预览估算成本，超阈值熔断（借鉴 GBrain $0.96→$50.71 事故教训） |
| **kill-switch** | 每类 LLM 调用可独立开关（提取/分层/rerank/维护） |
| **LLM 降级链** | LLM 不可用 → cosine 快路径 / 原样存储，语义检索永远可用 |
| **L0/L1 分层** | 默认只注入摘要层，省 token |

## 九、技术选型与落地建议

| 层 | 选型 | 理由/取舍 |
|---|---|---|
| 语言/框架 | Java 17 + Spring Boot（现有宪法四层） | 与 df-app 一致，复用基建 |
| 关系存储 | MySQL（现有库，逻辑分库） | 零新基础设施；节点/边/审计/经验都是关系型 |
| 向量存储 | **可插拔**：Qdrant（推荐）→ Milvus → 复用 OpenViking | MySQL 无原生 pgvector；Qdrant 轻量好运维 |
| BM25 | MySQL fulltext 或 ES（若已有） | 词法兜底，英文/中文需分别配置分词 |
| 消息 | 复用 Kafka `df.code.agent.message` | 零侵入摄取 |
| 检索接口 | REST + MCP（对齐现有 MCP 生态） | find/remember/search/read/grep 等标准工具 |
| 异步管线 | df-app 现有 Crane 定时任务 + 自建队列 | 维护循环用 Crane（单实例安全），摄取用队列 |

### 落地路线图（对齐 df-app 演进风格：每步可独立上线）

1. **MVP**：`mem_node` 文档树 + issue 记忆主干 + chat 摄取（原样存储，无 LLM）→ 路径检索 + BM25。验收：issue 详情页能看到记忆树，能按路径/关键词检索。
2. **检索升级**：加向量 + 混合召回 + RRF + 意图分类；`explain` 可观测。
3. **提取升级**：LLM ADD-only 事实提取 + 实体链接 + 分层 L0/L1/L2。
4. **图谱**：零 LLM typed edges + 关系查询 arm。
5. **飞轮**：issue 完成经验提炼 + 复用注入 + 维护循环（去重/纠错/浓缩/矛盾检测）。
6. **治理**：多租户细化 + 成本档位 + 审计查询 + 反馈修正。

## 十、风险与取舍

| 风险 | 缓解 |
|---|---|
| **ADD-only 存储膨胀** | 过期归档机制（stale/archived）、`mem_change_log` 只记 diff、L0/L1 独立于 L2 生命周期 |
| **LLM 提取幻觉污染记忆** | 低置信标记 + 人工确认工作流（记忆浏览器）、审计可回滚、`create_safety` 提示 |
| **向量库新增基础设施** | 可插拔抽象（BaseVectorStore），MVP 可先纯 BM25 上线再补 |
| **图谱零 LLM 覆盖有限** | 正则规则持续扩充 + schema pack 提供 `extraVerbs`；规则不覆盖的走语义通道兜底 |
| **经验复用的"错误经验"** | eta 复用度评分 + 适用边界(boundary)声明 + 反例收集 + 人工/团队 review |
| **AGPL 合规**（若借 OpenViking） | 默认方案 A 自建，避免商用风险 |
| **多用户误越权** | 存储层前缀强制 + 权限测试（fuzz 全读路径零泄漏，GBrain 纪律） |

---

## 十一、结论

本设计取四项目之长，围绕"**issue 驱动的团队记忆**"形成完整闭环：

- **组织形态**（OpenViking）：文档树确定性寻址 + L0/L1/L2 分层，省 token、可审计；
- **写入策略**（Mem0）：ADD-only 单遍提取 + 检索排序承载更新，写入快、历史全；
- **关系推理**（GBrain）：零 LLM typed edges 知识图谱，关系查询确定可答；
- **经验飞轮**（MemOS + OpenViking）：issue 完成→提炼经验→同类复用，越用越聪明；
- **治理底线**（GBrain/Mem0/OpenViking）：成本档位、存储层隔离、变更审计、异步管线。

它可以作为通用架构独立实现，也可按 §九 路线图分六步嵌入 df-app，每步可独立上线、可验证。
