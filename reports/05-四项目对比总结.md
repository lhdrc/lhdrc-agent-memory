# 四项目对比总结报告

> 对比对象：GBrain ｜ Mem0 ｜ MemOS ｜ OpenViking
> 调研日期：2026-08-02 ｜ 语言：中文
> 本文汇总四份独立调研报告（`01`~`04`），从多个维度横向对比，并提炼对"团队项目记忆系统"设计最有价值的结论。

## 一、一览总览

| 维度 | GBrain | Mem0 | MemOS | OpenViking |
|---|---|---|---|---|
| **一句话定位** | Agent 的"大脑层"：综合回答 + 图谱 + 差距分析 | AI 的记忆层：个性化长期记忆 | Agent 的"记忆操作系统"：统一存/取/管 | Agent 的"上下文数据库"：虚拟文件系统 |
| **开发者/背景** | Garry Tan（YC CEO，个人自用） | mem0ai（YC S24 公司） | MemTensor 团队 | 火山引擎/字节跳动 |
| **许可证** | MIT | Apache 2.0 | Apache 2.0 | AGPLv3（主项目） |
| **核心语言/栈** | Bun/TypeScript + Postgres/pgvector（PGLite WASM） | Python + TS，30 向量库/24 LLM 可插拔 | Python/FastAPI + Neo4j + Qdrant | Rust + C++ + Python 混编 |
| **记忆组织心智模型** | 数据库（brain/source 双轴）+ 知识图谱 | 事实条目 + 实体链接（弱图） | 记忆 Cube（多记忆类型组合） | 虚拟文件系统（viking://）+ 分层 L0/L1/L2 |
| **记忆写入策略** | 页面落库 + 零 LLM 自动建边 | **ADD-only 单遍提取**（不覆盖） | 多类型提取 + 偏好写入即 LLM 去重判定 | schema 驱动提取 + merge_op 语义合并 |
| **检索策略** | 四路召回（vector/BM25/graph/relational）+ RRF + reranker | 三信号融合（语义+BM25+实体） | 图+向量+BM25+全文 多路 + reranker + reasoner | 目录递归检索 + 分层加载 + 意图分析 |
| **团队/多用户** | OAuth 2.1 + SQL 层隔离 + source 粒度（强） | user/agent/run 四维过滤，OSS 无 RBAC | user↔cube 多对多 + 4 级角色 | account/user/peer 存储层强制前缀（强） |
| **记忆演化/闭环** | dream cycle 9 阶段（夜间富化/去重/纠错） | 无（靠检索排序承载更新） | MemScheduler + Reflect2Evolve（L1→L2→L3→Skill） | session commit 异步提取 + memory_diff 审计 |
| **成本意识** | **一等公民**：search mode 档位 + cost cap + 熔断器 | 报告 token/延迟，ADD-only 省提取延迟 | 异步调度省阻塞，72% token 宣称 | L0/L1/L2 分层省 token（最多 -91%） |
| **评测文化** | 强：LongMemEval/BrainBench + 诚实披露 | 强：LoCoMo/LongMemEval/BEAM + 开源复现 | 中：OmniMemEval 自建框架 | 中：LoCoMo/tau2 官方博客，无第三方复现 |

## 二、核心理念对比：四种"记忆观"

四个项目对"记忆应该是什么"有截然不同的回答，这是它们所有设计差异的总根源：

| 项目 | 记忆观 | 核心比喻 | 对"记忆"最看重的性质 |
|---|---|---|---|
| **GBrain** | 记忆 = 数据库 + 知识图谱，Agent 可以"思考"它 | 大脑层 / Brain | 可查询、可推理、可自我维护（差距分析告诉你还缺什么） |
| **Mem0** | 记忆 = 可复用的独立事实集合 | 个性化层 | 提取质量、检索精准、token 高效 |
| **MemOS** | 记忆 = 操作系统资源，可组装可调度 | 操作系统 | 类型多样性、可管理性、演化能力 |
| **OpenViking** | 记忆 = 文件系统里的可寻址文档 | 上下文数据库 | 确定性、可浏览、可审计、省 token |

**关键洞察**：四者其实互补。GBrain 重"推理与自维护"、Mem0 重"提取与检索的算法工程"、MemOS 重"管理与演化"、OpenViking 重"组织形态与成本"。

## 三、记忆写入策略对比

| 项目 | 写入机制 | 是否覆盖 | 更新语义 | 去重/矛盾处理 |
|---|---|---|---|---|
| **GBrain** | 页面落库 + auto-link 建图；facts 抽取走 hot memory 快路径 | 不覆盖，永不 DELETE | dream cycle 里 consolidate（事实→综合观点），修订 citation | cosine 0.95 快路径去重，LLM 降级 0.92 |
| **Mem0** | **ADD-only 单遍 LLM 提取**，一次调用只做新增 | 不覆盖 | 新旧并存，靠检索排序把最新/最相关排前 | MD5 哈希去重 + 提取 prompt 里语义等价跳过 |
| **MemOS** | 多类型提取（文本/偏好/图/技能），偏好写入即 LLM 去重判定 | 部分覆盖（偏好） | 偏好有 update 判定，TreeText 图记忆靠 soft_delete+evolve | LLM 判定 duplicate/update + 与文本记忆查重 |
| **OpenViking** | schema 驱动提取，LLM 去重决策 + merge_op 语义合并 | 部分覆盖（merge_op） | immutable/patch 字段级合并，版本号递增 | 两级去重（candidate 级 + item 级），memory_diff 审计 |

**值得注意的趋势**：**Mem0 的 ADD-only 与 GBrain 的"永不 DELETE"殊途同归**——都倾向"保留历史，靠检索排序决定显隐"，因为写入端的合并/覆盖决策是 LLM 最容易出错的地方。而 OpenViking 的 merge_op 与 MemOS 的偏好判定代表了"结构化更新"路线，代价是更复杂的管线。

## 四、检索算法对比

| 项目 | 召回方式 | 融合/排序 | 特色机制 |
|---|---|---|---|
| **GBrain** | vector + BM25 + 图谱边 + relational arm 四路 | RRF(k=60) + cosine re-score(0.7/0.3) + source 加权 + reranker(zerank-2) | 意图分类、query 扩写、graph signals（hub/cross-source/session demote）、per-page max-pool |
| **Mem0** | 语义为主（over-fetch），BM25 与实体仅 boost | 归一化后加权和（自适应分母），阈值前置 | 查询长度自适应 sigmoid、实体 boost(0.5 权重×链接衰减)、`explain=True` 可观测 |
| **MemOS** | 图(key/tags) + 向量 + BM25 + fulltext 四路 | 按 ID 合并 + 层级加权 rerank + reasoner 校验 | TaskGoalParser 拆解 query、子图召回、偏好双集合并行 |
| **OpenViking** | 目录级向量定位 + 递归下钻 | alpha 分数传播 + rerank | 意图分析(TypedQuery)、hotness 冷热混合、L0/L1 作为预筛层 |

**关键洞察**：
1. **混合检索是共识**：四个项目无一单靠向量，都上了 BM25（词法兜底）+ 至少一种第二信号。
2. **GBrain 的图谱召回最"硬核"**：typed edges + 关系查询 arm 是四者里唯一真正做关系推理的（Mem0/MemOS 的图都是共现/标签级弱图）。
3. **OpenViking 的"目录级检索"是独特的召回组织方式**：其他三者都是平面召回，只有它按目录下钻保留上下文。
4. **归一化工程是 Mem0 的独特贡献**：把量纲不同的信号融合成可比分数的工程细节（自适应 sigmoid + 自适应分母）是可复用的通用做法。

## 五、团队/多用户能力对比

| 项目 | 隔离模型 | 权限模型 | 团队场景成熟度 |
|---|---|---|---|
| **GBrain** | source 粒度 + brain 挂载；SQL 层强制 | OAuth 2.1 + scope + slug 前缀绑定 + 预算限额 | **高**（company-brain 是官方主打教程，fuzz 测试零泄漏宣称） |
| **Mem0** | user/agent/app/run 四维 filter | OSS 无 RBAC；Server 有 API Key + 审计；Platform 有 Project 成员角色 | 中（OSS 形态团队能力弱，需上 Server/Platform） |
| **MemOS** | cube 隔离 + readable/writable | user↔cube 多对多 + ROOT/ADMIN/USER/GUEST 4 级 | 中（cube 模型灵活但运维重） |
| **OpenViking** | account/user/peer 三级，存储层自动加前缀 | api_key/trusted 模式 + 3 级角色 | **高**（多租户是存储层第一公民，VikingBot 管理大量终端用户） |

**关键洞察**：
- **GBrain 与 OpenViking 把多用户隔离当架构目标而非补丁**：一个在 SQL 层强制、一个在存储层强制，这正是团队系统最该学的"隔离由架构保证"。
- Mem0 的多维身份（user/agent/run/app）是**最细粒度的记忆归属模型**，尤其 `run_id`（会话/工单）与 `agent_id`（哪个 agent 说的）——这跟你们平台的"会话/沙箱/agent"模型天然契合。

## 六、记忆演化与"飞轮"对比

| 项目 | 演化机制 | 维护方式 | 飞轮强度 |
|---|---|---|---|
| **GBrain** | dream cycle 9 阶段（合成/抽取/模式/浓缩/纠引用/矛盾检测） | 夜间 cron 自主维护 | **强**：记忆自我修复、自我增值，"醒来比睡去聪明" |
| **Mem0** | 无独立演化层，靠检索排序 + 用户 update/delete | 无 | 弱（写端简单，靠读端兜底） |
| **MemOS** | Reflect2Evolve：轨迹→策略→世界模型→Skill 结晶 | 异步调度 + reward 反传 | **强**：最完整的"记忆自学习"闭环设计 |
| **OpenViking** | session commit 异步提取 + merge_op 演化 + session train | 异步管线 + 审计 | 中强：经验/轨迹记忆可复用、可自我改进（tau2 实证） |

**关键洞察**：
- **GBrain 与 MemOS 代表了"记忆维护"的两条路线**：GBrain 是"夜间批处理维护"（确定性规则为主），MemOS 是"持续在线演化"（LLM 归纳为主，成本更高）。
- OpenViking 的 **experience/trajectory 记忆是"经验复用"的实证**（tau2 +6.87~+11.87pp）——这正是你们平台"issue 驱动的任务"最需要的：**做过的任务沉淀成可复用经验，下个任务直接受益**。

## 八、各项目优缺点一句话总结

| 项目 | 最值得学 | 最大短板 |
|---|---|---|
| **GBrain** | 零 LLM 图谱 + 夜间自主维护 + 成本一等公民 + 契约工程 + 诚实评测 | 单机导向、图遍历 v1、temporal 弱、macOS 偏好 |
| **Mem0** | ADD-only 提取 + 混合检索归一化工程 + 向量库内嵌实体链接 + prompt 即规格 | ADD-only 导致知识更新并存、OSS 团队能力弱、仅英文实体 |
| **MemOS** | 记忆类型插件化 + 偏好写入去重判定 + 异步调度 + Reflect2Evolve 演化 | Parametric 未实现、依赖重、图更新不支持、两套体系不统一 |
| **OpenViking** | 文件系统组织 + L0/L1/L2 分层省 token + 目录级检索 + 存储层多租户 | Alpha 阶段、AGPL、LLM 依赖重、无第三方复现 |

## 九、对"团队项目记忆系统"的综合结论

结合你的平台背景（团队空间、沙箱执行 agent、issue 驱动任务、共享 session、df-app 架构），四个项目给出的设计启示可归纳为"取其长的四条主线"：

### 1. 组织形态：取 OpenViking —— 可寻址的文档树 + 分层加载
团队记忆天然按项目/主题/会话/成员组织。`viking://` 式的确定性路径 + L0/L1/L2 分层，是省 token、可审计、可人工整理的关键工程手段。issue 驱动的任务天然形成"每个 issue 一条记忆子树"的结构。

### 2. 写入与更新：取 Mem0 —— ADD-only 提取 + 检索排序承载更新
把"提取与更新决策"从两遍 LLM 压缩为一遍，记忆只增不覆盖，靠检索把最新/最相关排前。对"信息变更频繁但历史有用"的团队场景（方案迭代、偏好漂移、经验演进）更稳。**但需配过期/归档机制控制膨胀**。

### 3. 关系与复用：取 GBrain —— 零 LLM 知识图谱 + 关系查询
typed edges（项目→成员、issue→方案、agent→产出）用确定性正则构建，让"谁做过什么""哪个 issue 用了什么方案"这类关系查询不依赖 embedding 重训。配合夜间维护循环（去重/纠错/浓缩），形成记忆飞轮。

### 4. 经验演化：取 MemOS 的 Reflect2Evolve / OpenViking 的 experience memory
把"某类 issue 的解决过程"沉淀为可复用轨迹/经验，下次同类任务直接检索注入（tau2 +11.87pp 的实证）。这是你们"issue 驱动任务"平台最直接的飞轮——**做过的任务成为下个任务的输入**。

### 跨项目通用底线
- **成本是一等公民**（GBrain）：search mode 档位 + cost cap + 熔断器，多用户共享系统必备；
- **多用户隔离由存储/DB 层强制**（GBrain/OpenViking）：不是 UI 隐藏，而是架构保证；
- **可观测与审计**（Mem0/OpenViking）：`explain` 分数、history/memory_diff 变更审计、检索轨迹；
- **异步写入管线**（MemOS/OpenViking）：写入不阻塞主链路，异步提取 + 状态跟踪 + 失败重试；
- **评测纪律**（Mem0/GBrain）：报告 token/延迟而非只报准确率，明确口径，可复现。
