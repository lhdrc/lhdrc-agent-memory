- **团队**：mem0ai，**Y Combinator S24** 公司（`README.md:38`）。
- **许可证**：Apache 2.0。
- **论文**：*Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory*（arXiv:2504.19413，2025）。
- **一条产品线三种交付形态**（`README.md:109-115`）：

| 形态 | 方式 | 适用 |
|---|---|---|
| Library（OSS SDK） | `pip install mem0ai` / `npm install mem0ai` | 测试/原型，最轻，自备 LLM + 向量库 |

## 二、核心理念与理论

### 2.1 Messages vs Memories：存事实，不存原文

默认 `infer=True` 时，Mem0 用 LLM 把对话"提炼成可复用的独立事实"存储，而非逐字保存 transcript（`docs/core-concepts/how-it-works.mdx`）：

- `"I prefer aisle seats"` → `User prefers aisle seats`
- `"Let's use Postgres for this project"` → `Project decision: use Postgres`

两阶段使用模式：交互后 `add` 写入，模型调用前 `search` 读取。

### 2.2 分层记忆（`docs/core-concepts/memory-types.mdx`）

| 层 | 生命周期 | 用途 |
|---|---|---|
| Conversation memory | 单次响应 | 工具调用、chain-of-thought |
| Session memory | 分钟~小时 | 多步任务（`run_id` 隔离） |
| User memory | 周~永久 | 个性化偏好 |
| Org memory | 全局配置 | 多 agent 共享知识 |

### 2.3 v3 算法哲学（2026 年 4 月，当前主线）

- **ADD-only：记忆只增不覆盖**。信息变化时（如搬城市）新旧事实并存，靠检索排序让"最相关的当前信息"排前面（`docs/migration/oss-v2-to-v3.mdx`）。旧算法两次 LLM 调用（提取候选 + 决定 ADD/UPDATE/DELETE），新算法**单次 LLM 调用只做 ADD**，模型算力花在理解输入而非 diff 旧记忆。
- **Agent 生成的事实也是一等公民**：assistant 说的"我帮你订好航班"也会被提取存储（旧算法常忽略）。
- **图记忆内置**：v3 移除外部图数据库（Neo4j 等 ~4000 行代码），改为在 add 时从记忆自动提取实体，存入同名向量集合 `{collection}_entities`，共享实体的记忆互相链接；检索时 boost 关联记忆。**影响排序、不改变响应形状**。
- **优雅降级**：spaCy 缺失 → 无实体/无 BM25 词形还原；fastembed 缺失 → 无 BM25；实体集合不可用 → 无实体 boost。**语义检索永远可用**。

## 三、架构

### 3.1 Provider 模式

每个能力类别有抽象基类 + 多 provider 实现，全部可插拔：LLM（`mem0/llms/base.py`）、Embeddings（`embed` 带 memory_action add/search/update）、Vector Store（`search` 须返回 [0,1] 相似度，v3 新增 `keyword_search` 与 `search_batch`）、Reranker、History DB（SQLiteManager，`history` 表记录 add/update/delete 变更历史）。

统一入口：`Memory`（同步，`main.py:463`）与 `AsyncMemory`（`main.py:2137`）。

### 3.2 三存储模型

- **SQL 数据库**（SQLite `history.db`）：事实 + 元数据 + 变更历史；
- **向量数据库**：嵌入向量，语义相似检索；
- **Entity/Graph Store**（`{collection}_entities`）：实体 + linked_memory_ids，v3 内置图记忆。

### 3.3 Self-Hosted Server

FastAPI 单体：JWT 认证（默认开启）、限流、请求日志（`RequestLog`）、dashboard（审计日志/记忆浏览/实体管理/API Keys/配置覆盖）。Docker Compose：mem0 + pgvector:pg17 + dashboard。

## 四、记忆核心实现（add / search / update / delete / history）

> 全部在 `mem0/memory/main.py`（3821 行）。

### 4.1 add() 的 V3 八阶段流水线（`_add_to_vector_store`，887 行起）

| Phase | 内容 |
|---|---|
| 0 | 上下文收集：取最近消息（`db.get_last_messages`，limit=10） |
| 1 | 现有记忆检索：语义 top_k=10（同作用域），UUID 映射成 `"0","1"...` 防幻觉 |
| 2 | **单次 LLM 提取**：`ADDITIVE_EXTRACTION_PROMPT` + 丰富上下文（Summary/Last k Messages/Existing Memories/Observation Date/Current Date/可选语言），要求 `json_object`，解析 `{"memory":[{id,text,attributed_to,linked_memory_ids}]}` |
| 3 | 批量嵌入（失败逐条回退） |
| 4/5 | **MD5 文本哈希去重**（对库 + 批内 seen） |
| 6 | 批量持久化（失败逐条回退）+ history |
| 7 | 批量实体链接（提取 → 去重 → 嵌入 → 匹配已有实体 exact 优先/语义≥0.95 → 更新 linked_memory_ids） |
| 8 | 保存消息 + 返回 |

- `infer=False`：跳过 LLM，原样入库（Direct Import）。
- `memory_type="procedural_memory"`：把对话总结成 step-by-step 程序性记忆（需 agent_id）。
- **提取质量约束**（`prompts.py`）：只提取有证据的独立事实；每个可记忆信息单独成条；相对时间锚定 Observation Date；语义等价则跳过；text 建议 15-80 词、自包含。

### 4.2 search() 的多信号融合（1350 行）

1. 预处理：`lemmatize_for_bm25(query)` + `extract_entities(query)`；
2. 嵌入查询；
3. 语义检索 **over-fetch** `max(limit*4, 60)`；
4. BM25 归一化（sigmoid，参数按查询长度自适应）；
5. 实体 boost（见 §5.4）；
6. 候选集 = 语义结果（过滤过期）→ `score_and_rank` 融合 → 格式化返回。

### 4.3 其他操作

- `get_all`：filters 必须含至少一个实体 ID（防跨用户混搜）；
- `update`：重新嵌入 + 写 UPDATE 历史 + **实体清理/重链**；
- `delete`：向量删除 + DELETE 历史 + 从实体记录剥离 memory_id；
- `history(memory_id)`：读 SQLite 变更历史——**每次变更可追溯**。

## 五、检索算法（核心亮点）

### 5.1 三信号融合（`mem0/utils/scoring.py`，全文 139 行）

```
combined = min((semantic + bm25 + entity_boost) / max_possible, 1.0)
```

- **阈值门槛前置**：semantic < threshold 直接剔除，即使 BM25/实体能拉高；
- **自适应分母**：按可用信号调整（语义-only→1.0；+BM25→2.0；+实体→2.5），保证输出 [0,1]；
- **BM25 是 boost 而非召回扩充**：候选集只有语义检索结果，BM25 与实体只改排序、不加新候选。

### 5.2 BM25 归一化：查询长度自适应 sigmoid

| 词数 | midpoint | steepness |
|---|---|---|
| ≤3 | 5.0 | 0.7 |
| ≤6 | 7.0 | 0.6 |
| ≤9 | 9.0 | 0.5 |
| ≤15 | 10.0 | 0.5 |
| >15 | 12.0 | 0.5 |

`sigmoid(raw)` 把无界 BM25 压到 [0,1] 与语义分可比。词形还原额外保留 `-ing` 原形处理名词/动词歧义（meeting vs meet）。

### 5.3 实体提取（`mem0/utils/entity_extraction.py`，772 行）

四类实体：PROPER（spaCy NER，排除数字时间标签）/ IDENTIFIER（`foo.bar.Baz` 技术标识符）/ QUOTED（引号内文本）/ TOPIC（复合名词短语）。大量工程化过滤（60+ 通用名词黑名单、~100 模糊形容词、span 冲突解决）。

### 5.4 实体 boost（`_compute_entity_boosts`，1704 行）

```
memory_count_weight = 1 / (1 + 0.001 * (num_linked - 1)^2)
boost = similarity * ENTITY_BOOST_WEIGHT(=0.5) * memory_count_weight
```

4 线程并行搜实体库（top_k=500），相似度 ≥0.5 才计；链接越多的记忆单条 boost 越低（防热门实体淹没一切）；实体信号最大贡献 0.5。

## 六、团队 / 多用户能力

- **四维身份**（`docs/platform/features/entity-scoped-memory.mdx`）：`user_id`（人）、`agent_id`（agent 人格）、`app_id`（租户）、`run_id`（会话/工单）。写入接受任意组合；默认提取路径上 user 消息只带 user_id、assistant 消息只带 agent_id。
- **OSS 多用户**：实体 ID 即向量集合内 filter，天然多用户隔离；`search`/`get_all` 强制至少一个实体 ID 防混搜。**无内置 RBAC/团队 UI**——那是 Server/Platform 的能力。
- **Server 团队能力**：per-user API Key（`m0sk_...` 仅显示一次，bcrypt 存前缀）、请求审计日志、Entities 管理（cascade-delete）。
- **Platform 团队**：`Project` 类提供 `add_member(email, role)` 成员/权限模型（角色至少 READER）、org/project 两级、feedback、webhooks、memory export。

## 七、数据支撑（Benchmark）

### 7.1 主数字（`README.md:47-54`）

| Benchmark | 旧算法 | 新算法 | 平均 token/query | 延迟 p50 |
|---|---|---|---|---|
| **LoCoMo** | 71.4 | **92.5** | 7.0K | 0.88s |
| **LongMemEval** | 67.8 | **94.4** | 6.8K | 1.09s |
| **BEAM (1M)** | — | **64.1** | 6.7K | 1.00s |
| **BEAM (10M)** | — | **48.6** | 6.9K | 1.05s |

- 口径：single-pass 检索（一次调用，无 agentic loop）、top_200 预算、生产代表模型栈；**平台分数含专有优化**。
- 迁移文档（`oss-v2-to-v3.mdx`）：LoCoMo 71.4→91.6、LongMemEval 67.8→93.4、提取延迟 p50 ~2.0s→~1.0s。

> **诚实提醒**：README 用 92.5/94.4，迁移文档用 91.6/93.4——同为官方数字差 ~1 分，口径需以各自上下文为准。

### 7.2 分维度明细（`docs/core-concepts/memory-evaluation.mdx`）

- LoCoMo：single-hop 91.2 / multi-hop 91.3 / open-domain 72.7 / temporal 92.0；
- LongMemEval：single-session(user) 98.6 / single-session(assistant) 98.2 / preference 96.7 / knowledge update 93.6 / temporal 97.0 / multi-session 88.0；
- BEAM 10M 崩的点：temporal_reasoning 61.8→16.3、event_ordering 53.6→20.2、multi_session_reasoning 65.2→26.1（文档自认全行业开放问题）。

### 7.3 评估方法论（对行业很有价值）

- 小基准饱和 ≠ 可扩展记忆系统；
- **token 效率与准确率同等重要**（95%@25K tokens ≠ 90%@7K tokens），必须报告每查询平均 token；
- 同约束比较：相同检索预算、相同模型、相同延迟预算；
- 注意天花板效应；**BEAM 10M 才是真正考验**。

### 7.4 复现路径

`evaluation/` submodule → `mem0ai/memory-benchmarks`，独立 runner 共享 CLI（`--backend oss|cloud`、`--top-k 200`、`--resume`）。

## 八、优点

1. **ADD-only 单遍提取**：把记忆写入从"提取 + 更新决策"两遍压缩为一遍，提取延迟减半、结果 +20/+26 分。模型算力全部花在理解输入而非 diff 旧记忆——本 repo 最核心的设计洞见。
2. **混合检索工程化程度高**：语义（候选）+ BM25（词形还原 + 查询长度自适应 sigmoid）+ 实体 boost（0.5 权重 + 链接数衰减）三信号融合，分母自适应、阈值前置、`explain=True` 可观测——不是简单拼接，是精心调参的算法。
3. **内置图记忆取代外部图数据库**：实体提取 + 链接全自动、零配置、与向量库同设施，无运维负担且优雅降级，对 SaaS 化是重大简化。
4. **生态纵深**：24 LLM / 30 向量库 / 15 嵌入 / 5 reranker provider，Python + TS 双实现，Plugin/MCP/Skills/CLI/REST 全链路，Apache 2.0。
5. **企业级工程纪律**：CI Gate 分包测试、OIDC 发布、pydantic v2、结构化错误码、请求审计日志、JWT+bcrypt API Key、批量回退容错。
6. **诚实的技术叙事**：区分 Platform 与 OSS 分数、承认 knowledge-update 软肋与 BEAM 10M 弱项、开放基准仓库、"报告 token/延迟而不只报准确率"。
7. **提取 prompt 即产品规格**：`prompts.py` 里几十个 few-shot 示例把提取行为约束得极其具体（归因/链接/时间锚定/自包含事实）。

## 九、缺点 / 局限

1. **LLM 依赖度 = 成本与延迟**：提取、去重、程序记忆、LLM reranker 都依赖外部 LLM；离线/私有部署成本高。
2. **ADD-only 的语义取舍**：记忆只增不改 → **知识更新场景旧事实永远并存**（LongMemEval knowledge update 93.6、BEAM 10M 崩到 16.3-26.1）。对"事实必须被纠正"的应用需应用层自己 update/delete。
3. **分数口径不一致**：92.5/94.4 vs 91.6/93.4 并存；`LLM.md` 大量 API 已过时，文档多处落后于代码。
4. **Platform 与 OSS 能力断层**：Temporal Reasoning、Memory Decay、Webhooks、Memory Export 均为 Platform 专属——"开源"叙事与"托管引流"并存。
5. **图记忆是"弱图"**：实体链接是共现图（schema-free、无类型化边），只做检索 boost，不做显式关系遍历；多跳主要靠实体 boost 间接效果。
6. **实体依赖 spaCy + 仅英文**：非英语场景实体链接基本失效。
7. **多租户/团队能力 OSS 基本没有**：OSS 只有实体 ID filter 隔离，无 RBAC/审计/团队管理——对"团队项目记忆"诉求，OSS 库形态勉强可用。
8. **`get_all` 无分页**；`history.db` SQLite 单机文件，无分布式历史存储。
9. **遥测默认开启**（PostHog）——团队内部部署需注意隐私。

## 十、可借鉴点（站在"团队项目记忆系统"角度）

1. **ADD-only + 检索排序承载"更新语义"**：与其在写入端做复杂合并决策，不如全量保留 + 靠检索把最相关/最新事实排前面。**代价是存储膨胀，需配过期/清理机制**。
2. **混合检索的归一化工程**：BM25 与余弦量纲不同，直接相加无意义。借鉴 sigmoid 自适应归一化 + 自适应分母 + 阈值前置，这是可复现的通用做法。
3. **实体链接作为"图记忆"的轻量实现**：不部署 Neo4j，在向量库放 `{collection}_entities` 集合存"实体 → linked_memory_ids"，检索时 boost。团队记忆里的"项目名/人名/专有名词"这类强信号尤其适用。
4. **"提取 prompt 即产品规格"**：把记忆提取的行为约束全部写进 prompt 并随代码版本管理。LLM 记忆系统的核心逻辑在 prompt 而非代码。
5. **写路径健壮性**：批量嵌入/插入失败自动逐条回退、hash 双级去重、uuid 映射防幻觉、实体清理吞异常不阻塞主路径。
6. **可观测与审计**：`explain=True` 返回 score_details；history 表记录每次变更 old/new/actor——"某条记忆为什么被检索到 / 谁改过"是团队刚需。
7. **评估哲学**：报告 token + 延迟 + 多截断深度，同约束比较，承认天花板效应。
8. **Provider 抽象 + 优雅降级**：组件替换自由度高，语义永远可用，避免被单一厂商锁定。
