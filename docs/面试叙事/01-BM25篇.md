# df-memory 面试准备笔记 · BM25 字面检索篇

> 口径：独立完成本地记忆模块 df-memory 的字面检索一路，从选型、摄入、存储、检索到评测的完整闭环，能复述并解释每一个设计决策和踩过的坑。
>
> **卡片格式**：每张卡模拟面试官三轮追问，每轮给出原话提问和口语化作答。先自己试着答，再看参考。

## 30 秒开场介绍

df-memory 是单机本地部署的 agent 记忆模块，定位是 agent 的 git 加知识库。检索是核心能力，跑两条路：语义向量管意思相近的召回，BM25 字面检索管精确匹配。字面路完整跑在 PGlite 内嵌数据库的全文检索上。链路三段：摄入侧语义哈希判重加统一清洗；存储侧标题正文各存整词和 bigram 两轨，建 GIN 倒排，表达式索引物化，命中走位图索引扫描；检索侧问句用同一个函数切分，多臂加权打分，长度归一，交三路融合。中文是最大的坑，用字符二元滑窗分词解决，写入侧清洗加权重压制控噪音。评测三轮闭环：钉死的回归场景、每次改动都跑的小型评测集、可拆解的打分明细。

## 主线叙述（约三分钟）

**面试官：BM25 这一路是怎么做的？**

先说为什么做 BM25 这条路线。传统的 RAG 检索是用向量做存储和检索，向量检索的优势是能搜到语义相近的文字，但如果是一些精确的查询，比如说一串编号、一个具体的时间，用户就是要原文精确命中，向量按语义相似去找反而搜不准，因为编号和时间这种东西没有语义可以相近。于是我们用 BM25 字面检索来弥补这个缺陷，最终形成语义和字面两条检索路。

选型上我们用本地的 PGlite 来做存储和检索，理由有几个点。首先我们的项目设计就是记忆库 git clone 下来就能直接用，而不是从远程权威数据库拉取信息，PGlite 零依赖刚好满足这一点，它是一个嵌入式的 Postgres，直接跑在进程里，不用单独起数据库服务，数据就是本地的一个目录。在这个基础上，PGlite 对建索引有天然优势，它内置了全套的全文检索能力：文本可以用它自带的分词配置预处理成倒排格式，查询语句也有对应的格式，打分函数是现成的，倒排索引用 GIN 建，命中时走位图索引扫描，先用索引快速拿到一小批候选文档，再取出正文做精细排序。而且索引和文档存在同一个库里，写入在同一个事务里完成，不会出现文件改了、索引还是旧的这种中间状态，索引丢了也随时能从文件全部重建。这和我们的架构底线是一致的：文件才是真正的数据，索引只是根据文件生成出来的缓存，坏了删掉重建就行。

然后我说一下我们的链路是怎么样的，我通过三个大点来讲：摄入、存储、检索。

首先是摄入。一篇文章进来，先做去重，用 sha256 给每篇文章算内容哈希，和库里一比，完全一样的就直接跳过。这个哈希的内容只包含真正影响含义的字段，比如标题、标签、正文，时间戳这类每次保存都会变的字段不算进去，所以用户只是重新保存了一下文件，不会触发一次没有意义的重新摄入。

然后是文本清洗。这里我们一开始依赖的是 PGlite 自带的分词配置，它把英文按空格和标点切开、统一成小写，对英文语料效果是好的。但实际使用中发现了问题：我们摄入的文章是中英文混排的，这套配置只对英文有效，中文没有空格，分词器整句话把它当成一个词存进倒排。比如支付网关超时这六个字是一个整体，用户搜网关这两个字，解析出来是另一个词，永远匹配不上。中文的问题不是搜出来排序不好，是压根搜不出来。于是我们补充了 bigram 滑动窗口分词。它的做法是完全不管词典和语义，按相邻两个字符滑窗切，支付网关超时就切成支付、付网、网关、关超、超时这五个片段存进去，查询也按同样的规则切，搜网关就得到网关这个片段，正好能撞上中间那个位置。选它是因为不需要引入任何外部分词工具，中英文混在一起也能用，而且算法是确定的，同样的输入永远得到同样的输出，离线测试环境里可以完全复现。bigram 有个代价，词和词的接缝处会切出关超这种实际不存在的片段，搜出来的结果里会混进不相关的文档。我们的控制手段是在它前面先做清洗：全角转半角统一字符形态，代码块整体剔除，markdown 链接只保留显示文字，表格线这类排版符号全部去掉，先把假片段的主要来源掐掉。再用权重兜底，bigram 这一路的打分权重刻意给得比整词低，这样即使它带回一些噪音结果，排名也会排在整词命中的文档后面，不会被噪音带偏。代码块剔除是刻意的，一篇只在代码里出现过 retry 的文档，不应该和标题就叫重试的文档抢排名。这套清洗和分词，我们同样用在查询问句上：写入的时候用什么规则切，查询的时候就用同样的规则切，两边调用的是同一个函数，保证查询的词和存储的词能对上。这是全文检索最隐蔽的坑，两边处理规则只要有一点不一致，检索质量就会慢慢变差，而且没有任何报错，你很难发现是哪里出了问题。

然后是存储。每篇文章在索引表里占一行，除了原文，我把标题和正文各存两份文本列，一份是整词轨的文本，一份是中文轨的 bigram 文本，在这四个列上建 GIN 倒排索引。这里踩了第二个坑：我最初把分词转换直接写在查询语句里，查询时对文本列现场转换再匹配，功能是对的，但 EXPLAIN 一看执行计划是全表扫描。原因想通了很简单，转换发生在查询时，等于每次查询把全库文档重新分词一遍，倒排根本没帮上忙。解法是把转换挪到写入侧，在列上建表达式索引，这种索引在建索引的时候就把分词转换算好存进倒排结构。之后查询命中走的是位图索引扫描，先从倒排拿到一小批候选文档，再根据这批候选去取正文、算出准确的分数。我给这个优化写了一条硬性验收：EXPLAIN 的输出里必须出现位图索引扫描，防止以后的改动悄悄退化回全表扫描。

最后是检索。问句进来先做和写入完全相同的清洗和 bigram 切分，不做同义改写也不做扩写。字面检索要做的事情很单纯，就是忠实地把包含这些原文的内容找出来，理解用户真正想问什么、换种说法去找，那是语义那一路的职责，两边不该互相掺和。打分在一条 SQL 里算完，是六项加权加三个原串兜底。整词轨四项，标题命中权重 3.0，正文 1.0。每一项内部跑两遍，一遍只要求词都出现、不管顺序，一遍要求按原来的顺序连续出现，短语完整出现的情况下再额外加一项，标题 1.5、正文 0.5。为什么要分开，因为词都出现但顺序是乱的，和原句完整地出现，是两种强度不同的相关信号，混在一起算就把这个信息浪费掉了。bigram 轨两项接中文，标题 2.0、正文 0.8。原串兜底是拿用户输入的原文直接去匹配：出现在标题里加 2.5，出现在路径里加 1.5，出现在别名里加 3.0，别名是全场最高的分数，因为用户能一字不差地叫出这个别名，说明他就是要找这个东西，这是最强的意图信号。这三条是层层兜底的关系，整词切得对走整词，中文切不准走 bigram，就算前面全都没匹配上，还有原文包含判断兜底。分数最后除以正文长度的 0.3 次方做长度归一，防止长文档靠字数多堆分，然后排序取前 N 条，交给三条检索路共用的融合层。过滤条件也和另外两路用同一套，只搜活跃文档、只搜当前 brain，这是为了保证三条路筛选数据用的是同一套条件，不然融合出来的结果就不可比了。

长度归一这个系数是评测跑出来的。链路通了之后我们搭评测，一组钉死的回归场景，加一个小型检索评测集，每次改动都跑一遍，确认检索的排序质量没有变差。评测发现第三个坑：有一类超长的文档，靠字数多、正文里到处都能攒到词频，长期霸占第一位，真正相关的短笔记反而排在后面。根因是打分随着文档长度单调上涨，长文档天然有更多机会命中词。修复就是长度归一，总分除以正文长度的 0.3 次方。为什么取 0.3 而不是 BM25 经典的 0.75，因为 0.75 那种压法适合单路就决定最终结果的场景，我们这里最终名次由三条路融合裁决，单路只要排序大致对就可以了，压得太狠会把那些本来就长、但内容确实相关的文档误伤掉。取一个温和的值，把垄断压掉，把误伤控住。改完之后长文霸榜的回归用例转绿，评测集的排序也没有回退。

效果上，中文检索从完全搜不到到稳定命中，固定 3 次这种带空格的写法，也能命中正文里固定3次不带空格的写法，因为切分的时候空白被压缩掉了；代码块不再抢排名；命中判断从全表扫描变成位图索引扫描；长文档不再垄断头部。另外每一条结果的分数都能拆开看，标题贡献多少、正文贡献多少、bigram 贡献多少、别名贡献多少，调权重和排查问题都不用猜。整套东西全部跑在 PGlite 里，索引坏了删掉重建就行，没有引入任何外部服务或者外部组件。

## 追问卡片

### 卡 1. 你们检索这块整体怎么做的？为什么还要专门做一条字面检索的路？

**追问一：「你们记忆模块的检索是怎么做的？」**

我们的检索跑两条路。语义一路用向量，把文本切成段之后嵌入成几百维的向量，按余弦相似度找意思相近的内容，这是召回的主力。字面一路是 BM25 风格的检索，负责精确匹配。两条路各自召回一批排好序的候选，最后按名次融合成一份结果。之所以要两条路，是因为用户的查询天然分两种，一种给意思，一种给原文，任何一种技术都覆盖不了另一种。

**追问二：「向量检索不是也能搜到内容吗，为什么还要专门养一条字面的路？」**

因为向量对精确查询效果不好。它的原理是把文字压成向量，意思相近的文本在空间里距离就近。这对支付服务为什么挂了这种问法很有效，但对一串订单号、一个具体时间、一个专有名词这种查询，向量反而帮倒忙。编号这种东西没有语义可以相近，嵌入之后它和其他文本的距离基本是随机的，怎么搜都搜不准。BM25 是字面匹配，用户给什么字，就找包含这些字的内容，精确查询只有它能兜住。所以两条路是互补关系，不是二选一。

**追问三：「用户搜的时候，你们怎么判断这次该走字面还是走语义？」**

不判断，两条路都走。用户不会自己声明这次是精确查询还是意思查询，而且判断错了比不判断更糟。所以两路同时召回，融合层按名次合分。还有一个细节，每一路交出去的候选都比最终要的条数多。因为最终名次是融合层定的，如果单路只交刚好够数的候选，可能把本该进榜、但在这条路里排得靠后的文档提前砍掉。多交一些，把裁决权留给融合层。

### 卡 2. 检索的存储选型为什么是 PGlite？

**追问一：「检索的存储选型是怎么定的？为什么是 PGlite？」**

选型时对比过三条路，自建倒排索引、外挂搜索引擎、用存储层自带的全文检索。最终选 PGlite，也就是内嵌版的 PostgreSQL。理由有几个点。首先我们的产品形态是单机本地部署，设计上记忆库 git clone 下来就能直接用，不依赖任何远程服务。PGlite 零外部依赖，直接跑在进程里，不用单独起数据库服务，数据就是本地的一个目录，刚好满足这个形态。其次它对建索引有天然优势，PostgreSQL 的全文检索是内核原生能力，文本有标准的预处理格式，查询语句有对应的格式，打分函数是现成的，倒排索引用 GIN 建，命中走位图索引扫描。而且索引和文档在同一个库里，写入在同一个事务里完成，不会出现文件改了、索引还是旧的这种中间状态，索引坏了随时能从文件全部重建。

**追问二：「Elasticsearch 那种专业搜索引擎更成熟，为什么不用？」**

功能上确实全，但对我们的部署形态是负担。单机本地场景，为一条检索路多养一个常驻进程、多一套存储和备份，成本不成比例。更关键的是和架构底线冲突。我们的系统里文件才是真正的数据，索引只是根据文件生成出来的缓存，随时可以删掉重建。外挂引擎的索引存在另一个系统里，和文件不同源，要重建就得跨系统对齐状态，这条底线就守不住了。PGlite 的索引和文件在同一个库里，重建就是重新扫一遍文件、全量回填，干净。

**追问三：「自建一套倒排呢？倒排索引的原理又不复杂。」**

写一个最简版确实不难，一两天的事。但能跑和生产可用是两回事。词典怎么维护、文档更新了倒排怎么增量改、并发读写怎么处理、数据落盘怎么保证不丢，这些是数据库全文检索子系统几十年积累下来的工程问题，全部自己扛一遍，换来的收益只是打分公式更可控。我的判断是这个收益撑不起成本。所以站在 PG 全文检索上面写业务层，把力气花在真正有差异的地方，比如中文分词和清洗，这些 PG 原生能力覆盖不了，后面细讲。

### 卡 3. 一篇文章进来，摄入都做了什么？中文是怎么处理的？

**追问一：「一篇文章进来，摄入的流程是怎样的？」**

第一步先判重。给每个文件算一个 sha256 内容哈希，和库里存的比对，一样就整篇跳过。这个哈希只包含真正影响内容的字段，标题、标签、别名、正文这些，时间戳这种每次保存都会变的字段被排除在外。这是为了避免无意义的重摄，用户只是重新保存了一下文件，不应该触发一次完整的重建。第二步清洗，第三步分词，第四步落库建索引，这几步我在后面分开讲。

**追问二：「中文检索你们是怎么解决的？」**

这是整条字面路里最大的坑。一开始我没把中文当回事，一测就发现问题，搜网关两个字，库里明明有一篇支付网关超时的笔记，一行都搜不出来。排查下来在分词这步。PG 自带的分词对英文是好的，按空格和标点切，单词边界清楚，统一小写，搜起来没问题。但中文没有空格，分词器把支付网关超时这六个字当成一个整体存进倒排，用户搜网关，解析出来是另一个词，永远匹配不上。所以中文的问题不是排序差，是根本搜不出来。

我评估了三个方案。第一个上词典分词，像结巴分词那种，效果最好，但它要装 C 扩展，内嵌的 PostgreSQL 加载不了扩展，直接出局，而且还要多维护一份词典。第二个按单字切，每个字当一个词条，信息量太低，搜什么都是一堆噪音。第三个是 bigram，字符二元切分，完全不管词典和语义，按相邻两个字符滑窗切，支付网关超时就切成支付、付网、网关、关超、超时这五个片段存进去，查询也按同样的规则切，搜网关正好能撞上中间那个片段。选它是因为不引入任何外部工具，中英文混排通用，而且算法是确定的，同样输入永远同样输出，离线测试完全可复现。

**追问三：「bigram 会切出假片段，怎么控制？清洗的规则又是怎么定的？」**

bigram 的代价是跨词假片段。词和词的接缝处会切出关超这种实际不存在的词，搜出来的结果会混进不相关的文档。控制分两层。

第一层是分词之前先清洗，把假片段的来源掐掉。规则包括全角转半角、统一字符形态，代码块整体剔除，markdown 的链接只保留显示文字，标题符、引用符、列表符、表格线这些排版符号全部去掉。代码块剔除是刻意的，一篇只在代码里出现过 retry 的文档，不应该和标题就叫重试的文档抢排名。还有一层业务清洗，已作废的事实条目要从索引文本里抠掉，不然用户会搜到一条已经废弃的结论还排在前面，这是误导。

第二层是权重压制。bigram 路的打分权重刻意给得比整词路低，标题 2.0、正文 0.8，整词路是标题 3.0、正文 1.0。这样即使它带回一些噪音，排名也会排在整词命中的文档后面，不会被带偏。

清洗还有一条铁律，只做在写入侧，查询侧复用同一个函数。我最初考虑过查询时现洗，后来意识到两个问题。一是每次查询都洗一遍是纯浪费，二是写入和查询在两处做，规则早晚悄悄漂移，两边切的词对不上，检索质量慢慢变差，而且没有任何报错，很难发现是哪里出了问题。所以写入怎么切、查询就怎么切，两边调用同一个函数，一致性才有保证。

### 卡 4. 索引是怎么建的？性能上踩过什么坑？

**追问一：「索引的存储结构是什么样的？」**

索引在 PGlite 里就是几张表。核心的一张表，每篇文章一行，存路径、标题、正文原文、内容哈希、状态这些字段，另外加四个检索列。标题和正文各存两份文本，一份是清洗后的整词文本，一份是清洗后的 bigram 文本。在这四个列上建 GIN 倒排索引。倒排的意思是记录每个词出现在哪些文档里，查询时只查命中的那几个词对应的文档列表，不用扫全库。本质是拿写入时多花一点分词成本，换查询时不再全库扫描。

**追问二：「性能上踩过什么坑？」**

踩过一个很典型的坑。我最开始的写法，是把文本转换成检索格式的那个函数直接写在查询语句里，查询时对文本列现场转换再匹配。功能是对的，但用 EXPLAIN 看执行计划，发现是全表扫描。想通了很简单，转换发生在查询的时候，等于每来一次查询，就把整个库的文档重新分词一遍，倒排索引根本没帮上忙。

解法是把转换挪到写入侧，在这几列上建表达式索引。这种索引在建索引的时候就把转换算好，存进倒排结构里。之后查询命中走位图索引扫描，先从倒排拿到一小批候选文档，再根据候选去取正文、算出准确的分数。我给这个优化写了一条硬性验收，EXPLAIN 的输出里必须出现位图索引扫描，防止以后的改动悄悄退化回全表扫描。

**追问三：「文章更新了，索引怎么跟着变？」**

增量同步。文件进来先算内容哈希，和库里比，哈希没变说明内容没变，整篇直接跳过，一个字段都不写。哈希变了才重写，重写是整篇重来，标题和正文两条轨的检索文本全部重新清洗、重新分词、重新落库，在同一个事务里完成。文件被物理删除的话，索引行也跟着清掉。

为什么不做更细的增量，比如只更新变化的段落？因为单机记忆库的量级是几千到上万篇文档，一篇文档重算一遍成本很低，细粒度增量带来的复杂度和出错风险不划算。整篇重算是确定性的，不会出现半新半旧的状态，正确性优先。

### 卡 5. 一个问句进来，怎么变成排序后的结果？

**追问一：「一个问句进来，是怎么变成排序结果的？」**

问句进来只做两件事，去掉首尾空白，然后调用和写入完全相同的那个函数做清洗和 bigram 切分。不做同义改写不做扩写。字面检索要做的事情很单纯，就是忠实地把包含这些原文的内容找出来。理解用户真正想问什么、换一种说法去找，那是语义路的职责，两边不该互相掺和。

打分在一条 SQL 里算完，六项加权加三个原串兜底。整词路四项，标题命中权重 3.0，正文 1.0。每一项内部跑两遍，一遍只要求词都出现、不管顺序，一遍要求按原来的顺序连续出现，短语完整出现的情况下再额外加一项，标题 1.5、正文 0.5。为什么要分开算，因为词都出现但顺序是乱的，和原句完整地出现，是两种强度不同的相关信号，混在一起算就把这个信息浪费掉了。bigram 路两项接中文，标题 2.0、正文 0.8。原串兜底是拿用户输入的原文直接去匹配，出现在标题里加 2.5，出现在路径里加 1.5，出现在别名里加 3.0，别名是全场最高的分数，用户能一字不差地叫出这个别名，说明他就是要找这个东西，这是最强的意图信号。最后总分除以正文长度的 0.3 次方做长度归一，防止长文档靠字数多堆分，排序取前若干条，交给三条检索路共用的融合层。过滤条件也和另外两路用同一套，只搜活跃文档、只搜当前记忆库，保证三条路筛选数据用的是同一套条件，融合出来的结果才可比。

**追问二：「这些权重数值是怎么定下来的？」**

按信号强度排的。标题命中比正文命中强，因为标题是作者对内容的概括，标题命中基本就是主题相关，所以整词标题 3.0、正文 1.0。整词命中比 bigram 命中强，因为 bigram 是拿噪音换来的召回，所以压到 2.0 和 0.8。短语完整出现比词序乱强，所以短语那一项是额外的加分。原串兜底里别名最高，因为精确叫出别名是最强的意图信号，标题次之，路径再次之。这些值不是一次拍定的，是配合评测集反复调出来的。每一条结果的分数都能拆开看，标题贡献多少、正文贡献多少、bigram 贡献多少，调权重的时候能直接看到每一路的变化，不是盲调。

**追问三：「完整的 BM25 公式有词频项和逆文档频率项，你们的打分有吗？」**

词频的部分有，逆文档频率的部分没有。PG 的打分函数本身做了词频饱和，一个词在文档里出现越多分数越高，但增长是递减的，出现五遍和五十遍的差距远小于一遍和五遍，这正是 BM25 公式里 k1 参数控制的那部分。逆文档频率没有，也就是不区分稀有词和常见词的分量。

这是有意的取舍。单路的职责是把候选召回准、排序大致对，最终名次由三条路融合决定，融合层只看名次不看绝对分数，语义路已经承担了大部分语义区分的工作。如果以后语料规模上来需要补这一项，改动也是收敛的，逆文档频率只需要对召回回来的头部几百条做一次在线统计，只算这几条的词频，不需要维护全库的统计表。

### 卡 6. 效果怎么验证？评测发现过什么问题？

**追问一：「这一路的效果怎么验证？」**

三层。第一层是回归场景，一组钉死的用例：中文词能搜到中文内容，固定 3 次这种带空格的写法能命中正文里固定3次不带空格的写法，代码块不抢排名，长文档不垄断头部，每次改动全量跑。第二层是一组小规模的检索评测集，每次改动跑一遍，确认排序质量没有回退。第三层是打分可解释，每条结果带命中来源的标注，关键词命中、标题命中、路径命中、别名命中一目了然，排查问题和调权重都不用猜。

**追问二：「评测发现过什么真问题？怎么解决的？」**

发现过长文档霸榜。现象是一类超长的文档，靠字数多、正文里到处能攒到词频，长期占着第一位，真正相关的短笔记反而排在后面。根因是打分随文档长度单调上涨，长文档天然有更多机会命中词。

修复是长度归一，总分除以正文长度的 0.3 次方。为什么取 0.3 而不是 BM25 经典的 0.75，因为 0.75 那种压法适合单路直接决定最终结果的场景。我们这里最终名次由三条路融合裁决，单路只要排序大致对就可以，压得太狠会把那些本来就长、但内容确实相关的文档误伤掉。取一个温和的值，把垄断压掉，把误伤控住。改完长文霸榜的回归用例转绿，评测集的排序没有回退。

**追问三：「语料涨大了，这条路的瓶颈在哪？怎么办？」**

当前的量级，单机几千到上万篇文档，这套结构很宽裕，命中判断走倒排索引，打分只对候选算。真到十万级，第一个要盯的是位图索引扫描的效率。词项分布太散的话，索引命中率会下滑，执行计划可以监控到这个信号。必要时按记忆库拆索引，我们的多租户设计里每个记忆库本来就是独立存储的，拆分是自然边界。原则是先量化再动手，监控到位了，瓶颈出现之前数据会先说话。
