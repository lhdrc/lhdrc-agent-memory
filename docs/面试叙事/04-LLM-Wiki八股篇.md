## 30 秒开场介绍

LLM Wiki 是 Karpathy 在 2026 年 4 月提出的一个范式，五千多人 star 的一个纯文本 gist，不是软件。一句话：传统 RAG 每次提问都从原始文档重新检索、重新综合，知识不积累；LLM Wiki 让模型增量地构建和维护一个持久的维基，知识编译一次、持续保鲜。结构三层，原始资料层不可动，模型维护的维基层，规范说明层；操作三个，摄入、查询、体检。它是我们项目的基石：原文权威层就是原始资料层，蒸馏出的经验和技能就是模型维护的维基层，写入格式规范和提示词合同就是规范层，夜间维护就是体检循环。Karpathy 讲的是个人单作者场景，我们是团队多 agent，所以多补了并发写安全、租户隔离、可审查可回滚三道防线，等于把个人复利升级成组织复利。

## 主线叙述（约三分钟）

**面试官：说说你们项目的底层思想，为什么这么设计？**

先说思想源头。我们这个项目的基石是 Karpathy 在 2026 年 4 月提出的 LLM Wiki 范式。它本身不是软件，是一个几千人 star 的纯文本构想文件，设计成直接粘给你的 agent，让 agent 和你一起落地。但它把 agent 记忆这个问题的第一性原理讲透了。

它开头先拆了主流做法。现在大家用模型处理文档，基本都是 RAG 那条路：上传一批文件，提问时检索出最相关的几段，喂给模型现场综合出答案。这条路能用，但有一个致命的性质，模型每次都在从零开始重新发现知识。你问一个需要综合五份文档才能回答的问题，模型就得每次都把那五份文档重新找出来、重新拼一遍，上一次的综合结果完全不留下来。没有积累。ChatGPT 的文件上传、NotebookLM、绝大多数 RAG 系统，都是这个模式。

LLM Wiki 反过来。资料进来，模型不是把它编目等着以后检索，而是当场读掉，提取关键信息，融进一个已经存在的维基：更新相关的实体页面、修订主题综述、把新数据和旧结论的矛盾标出来。知识是编译一次、持续保鲜，不是每次查询重新推导。Karpathy 原话的比喻，维基是一个持久的、复利的产物，交叉引用已经建好，矛盾已经标出，综合已经反映了你读过的一切，每加一份资料、每问一个问题，它都变得更厚。

结构上它极轻，就三层。最底层原始资料，文章、论文、笔记，模型只读不改，这是真相的源头。中间是维基，模型生成的互相链接的 markdown 页面，模型完全拥有这一层，建页、更新、维护交叉引用。最上层是规范说明，一份写给模型看的文件，告诉它页面怎么组织、摄入和回答该遵守什么流程。原文有句话说得很准：这一层是把模型变成有纪律的维基维护者、而不是泛用聊天机器人的关键。

操作上三个循环。摄入，资料进来，读掉、写摘要页、更新索引、顺手改掉所有相关的旧页面，一份资料可能触碰十到十五个页面。查询，先答问题，答得好还有第二个动作，把这次的比较、分析、发现回填成新页面，好答案不该蒸发在聊天记录里。第三个是体检，定期检查页面之间的矛盾、被新资料超过的陈旧结论、没有入链的孤儿页、被反复提到却还没有自己页面的重要概念。为什么体检是这个范式的灵魂，Karpathy 讲得直白：维护知识库最磨人的不是读和想，是簿记，更新交叉引用、保持几十个页面一致，人类放弃维护知识库，就是因为维护成本涨得比价值快。模型不会厌烦、不会忘记更新交叉引用、一次能改十五个文件，维护成本接近零，知识库才第一次可能长期活着。他还把这个思想接回 1945 年 Vannevar Bush 的 Memex，说布什没解决的是谁来维护，LLM 把这一环补上了。

为什么是现在才成立，三个前提近两年才满足。一是上下文够长够便宜，一次读一批资料、跨十几个页面更新，以前做不到。二是模型的文件操作能力成熟了，可靠地建文件、改文件、维护链接。三是纯文本的可移植性，markdown 加目录就是全部基础设施，人能用编辑器看图谱，模型直接改文件，版本管理免费拿。

这个范式和我们的产品是什么关系，一句话，我们就是它的工程化和组织化。三层逐一对上：它的原始资料层，对应我们的原文权威层，所有摄入原文先落档案目录，模型只读不改，热路径只追加不覆盖；它的维基层，对应我们蒸馏出的经验和技能，以及每篇文档的摘要侧车，模型在会话里干活，沉淀回库，复利积累；它的规范层，对应我们的写入格式合同和提示词合同，模型不能自觉，写入一律过校验，蒸馏提示词里还加了空转门控，问自己这次能不能让未来的 agent 干得更好，答不上来就返回空。它的三个操作也逐一对上：摄入对应我们的三条摄入口，捕获、记忆、会话摄入，攒窗口编译入库；查询对应我们的三路混合检索，字面、语义、图，这一点和生态里最流行的本地搜索引擎 qmd 的思路完全一致，BM25 加向量加重排；体检对应我们的夜间维护，矛盾检测、孤儿页检查、反向链接补齐，全是机器做。它的 index 和 log 两个导航文件，对应我们的摘要侧车做内容目录，事件账本做时间线。

最后说我们比原文多解决的部分，这也是面试里最能体现增量价值的地方。Karpathy 的场景是单机单作者，一个人策展、模型簿记。我们是团队加多 agent，直接搬这个范式会撞上三堵墙，所以多补了三样。第一，并发写安全，多个 agent 同时写一个库不互删，热路径走带锁的写事务。第二，租户隔离，不同团队的内容物理分目录，权限在访问控制层把关。第三，可审查可回滚，文件是真相、git 做批量账本，每次变更能看差异、能回滚。一句话总结：这个范式回答了个人怎么让知识复利，我们回答的是一个组织怎么让知识复利。

## 追问卡片

### 卡 1. LLM Wiki 是什么？

**追问一：「LLM Wiki 是什么东西？」**

Karpathy 在 2026 年 4 月发布的一个构想文件，一个纯文本 gist，发布几天内就有几千人 star 和 fork。它不是软件，定位是直接粘给你的编码 agent，让 agent 和你一起把它落地成具体实现。它讲的是一个范式：让大模型增量地构建和维护一个持久的知识维基，而不是每次提问都从原始文档里重新检索、重新综合。一句话，知识编译一次、持续保鲜，不是每次查询重新推导。

**追问二：「它和普通的知识库笔记软件有什么区别？」**

两个区别。第一，谁是维护者。传统笔记软件里人写人维护，Obsidian 那类工具只是编辑器，维护靠人的自律，所以绝大多数个人知识库死在维护上。LLM Wiki 里模型是维护者，人只负责挑资料、提好问题、把方向，摘要、交叉引用、归档这些簿记活全部模型干。第二，知识是什么状态。普通笔记是一堆平铺的文档，LLM Wiki 要求页面互相链接、结论持续修订、矛盾被标出，它是一张活的网。Karpathy 自己的比喻，Obsidian 是开发环境，模型是程序员，维基是代码库。

**追问三：「一个构想文件而已，为什么值得当项目基石？」**

因为它把 agent 记忆这个问题的第一性原理讲透了。agent 的上下文窗口永远是瓶颈，超过窗口的记忆要活下去只有两条路，要么每次临时检索拼答案，RAG 路线，知识不积累；要么把知识沉淀成一个持续维护的结构化产物，Wiki 路线，知识复利。这不是笔记技巧，是两条架构路线的分岔。我们的产品就是第二条路线的工程化，而且验证了社区认可度：发布后几周内几千个 star，Google 几天后就出了供应商中立的开放知识格式，生态里长出了十几个实现。

### 卡 2. 它和 RAG 的本质区别是什么？

**追问一：「RAG 的问题到底出在哪？」**

出在知识没有状态。RAG 的流程是资料躺在那不动，提问时检索几段最相关的，模型现场综合。这带来三个后果。第一，重复劳动，一个需要综合五份文档的问题，每次问都要重新综合一遍，上次的结果不留下来。第二，跨源结论活不了，第一次综合出来的对比和分析，答案是散在聊天记录里的，下次连问题带推理重新来。第三，矛盾看不见，只有当前恰好检索到两个矛盾的片段时才能发现，没检索到就一直埋着。

**追问二：「LLM Wiki 怎么解决这三件事？」**

把综合从查询时挪到摄入时。资料进来当场消化，综合结论直接写进维基页面，之后新资料来了是在已有结论上增量修订，不是从零再来。跨源分析同理，一次问出来的对比可以回填成页面，探索也在复利。矛盾是主动管理的，摄入新资料时就去更新相关的旧页面，新旧冲突当场标出，体检循环还会定期回看。用 Karpathy 的原话说，交叉引用已经建好，矛盾已经标出，综合已经反映你读过的一切，这是一个复利的产物。

**追问三：「那 RAG 是不是就没用了？两者怎么选？」**

不是替代是分工，分界在规模。社区的经验值，资料量在几百个页面以内，一个维护良好的索引文件就够了，模型先读索引再翻页面，连向量检索都不用上。到几万到十万 token 的维基，加一层本地混合检索就够。真正的海量资料，几百万 token 以上，那才是传统 RAG 的主场。我们项目是两者的结合体，而且顺序是关键：先蒸馏沉淀、再按需检索，检索的三路混合负责在沉淀层上快取，沉淀管线负责让知识先变成形态。这和 Karpathy 原文自己推荐的演进路径一致，他也是说维基大了之后才引入搜索引擎。

### 卡 3. 三层架构分别是什么？

**追问一：「三层各是什么？」**

最底层原始资料，文章、论文、笔记、数据文件，模型只读不改，这是真相源头。中间维基层，模型生成的互相链接的 markdown 页面，摘要页、实体页、概念页、对比分析页、总览页，模型完全拥有这一层，人只读。最上层规范说明，一份写给模型的文件，定义页面结构、命名约定、摄入和回答的流程。三层用一句话记：原始层是真相，维基层是理解，规范层是纪律。

**追问二：「原始层为什么必须不可变？」**

两个原因。第一，这是整个体系的错误兜底。模型生成的内容可能有错，如果原始层可改，错误就污染了真相源头，所有派生层全部失真，没有退路。原始层不可变，错误最多发生在派生层，派生层错了可以依据原始层重修。第二，这是信任的锚点。维基里的每个结论都能回溯到原始依据，人对系统的信任建立在可验证上。所以我们的实现里原文权威层模型只读不改，遗忘是软归档不是删除，热路径追加不覆盖。

**追问三：「规范层为什么是关键？」**

原文有句很准的话：这一层是把模型变成有纪律的维基维护者、而不是泛用聊天机器人的关键。模型没有纪律约束的话，每次摄入的页面格式漂移、链接随手建、目录各写各的，几十轮之后维基就散了。规范层把结构、命名、工作流写死，模型每次都按同一套纪律干活，而且人和模型可以共同演进这份规范。我们的对应是写入格式合同，所有写入过校验，模型不能自觉，还有提示词合同里的空转门控，摄入前先问自己这次能不能让未来的 agent 干得更好，不能就返回空，防止垃圾沉淀。

### 卡 4. 三个操作是怎么运转的？

**追问一：「摄入是怎么做的？」**

资料放进原始层，让模型处理。典型流程：模型读资料，先和你讨论要点，然后写一份摘要页进维基，更新索引，再把维基里所有相关的实体页、概念页顺手更新掉，最后在日志里记一笔。一份资料可能触碰十到十五个页面，这个触碰面就是它和普通笔记工具的本质区别，新知识是织进网里的，不是堆上去的。Karpathy 自己偏好一份一份摄入、全程参与，也支持批量低监督，看使用者的风格，把流程写进规范层就行。

**追问二：「查询有什么特别的？」**

查询不只是答问题。模型先读索引定位相关页面，翻页面综合出带引用的答案，然后有一个关键动作：答得好的内容可以回填成新页面。你让模型做的一个对比、一次分析、一个发现，是有价值的，不该蒸发在聊天记录里，回填之后你的探索也在给知识库复利，和摄入的资料享受同等待遇。

**追问三：「体检为什么是这个范式的灵魂？」**

因为簿记是人类放弃知识库的根因。Karpathy 的原话，维护知识库最磨人的不是读和想，是簿记，更新交叉引用、保持几十个页面一致、标出矛盾，人类放弃维护是因为维护成本涨得比价值快。模型不会厌烦、不会忘记更新交叉引用、一次能改十五个文件，维护成本接近零，知识库才第一次可能长期活着。体检的清单很具体：页面间矛盾、被新资料超过的陈旧结论、没有入链的孤儿页、被反复提到却没有自己页面的重要概念、缺失的交叉引用。这就是为什么我们项目把夜间维护做成一级能力，矛盾检测、孤儿页检查、反向链接补齐全是机器做。

### 卡 5. 这个思想怎么映射到你们项目？

**追问一：「三层在你们项目里对应什么？」**

原始资料层对应我们的原文权威层，所有摄入的原文先落档案目录，模型只读不改，低层热路径只追加不覆盖，遗忘走软归档。维基层对应我们蒸馏出的经验和技能，加上每篇文档的摘要侧车，会话里模型干活，蒸馏成可复用的经验沉淀回库，摘要随内容增量修订。规范层对应我们的写入格式合同和提示词合同，写入过校验，蒸馏有纪律。

**追问二：「三个操作对应什么？」**

摄入对应三条摄入口，单条捕获、一条记忆的快速入库、会话摄入攒窗口后编译，编译时模型消化对话、提炼事实、建实体、抽关系，对应一份资料触碰多个页面的织网动作。查询对应三路混合检索，字面、语义、图，问句先进来打分融合，答完还能引用到出处。体检对应夜间维护，矛盾检测、孤立页检查、实体反向链接补齐，这些全是机器在维护循环里做，不需要人推。

**追问三：「index 和 log 两个导航文件对应什么？」**

index 是内容目录，回答问题时先读它再翻页面。我们对应摘要侧车加分层索引，每篇文档有摘要层，检索先扫轻的再下钻重的，等于把单文件的索引升级成了数据库引擎。log 是时间线，追加式记录每次发生了什么。我们对应事件账本，每次摄入、合并、蒸馏都有事件，还做了历史的正排侧车，时间线可查、可审计。原文里说日志用统一前缀就能被命令行工具解析，我们是同一个思想，只是把纯文本日志升级成了结构化事件。

### 卡 6. 我们比原文多解决了什么？边界在哪？

**追问一：「Karpathy 的范式有什么你们必须补的？」」

他讲的是单机单作者，一个人策展、模型簿记。我们是团队加多 agent，直接搬会撞三堵墙。第一，并发写安全，多个 agent 同时写一个库会互删，我们热路径走带锁的写事务，批量变更走单独提交。第二，租户隔离，不同团队的内容物理分目录，读取有访问控制，git 历史对同库可见这点也在文档里明示，不是密码学隔离。第三，可审查可回滚，文件是真相、git 做批量账本，每次变更能看差异能回滚。一句话，把个人复利升级成组织复利。

**追问二：「模型写知识库，幻觉复利怎么办？」** 

这是社区讨论里最尖锐的问题，有评论直接说，幻觉会被永久固化成事实。我们的防线四层。第一层，原始层不可变，错误最多污染派生层，可以依据原文重修。第二层，派生内容带来源，蒸馏出的事实带原始出处引用，能回溯验证。第三层，矛盾治理，跨文档矛盾会被检测出来进冲突清单，较旧的一方检索降权，冲突支持人工裁决，裁决后旧结论标记被取代。第四层，热路径低层只追加不覆盖，所有蒸馏写入过格式校验。幻觉不可能归零，但可以被发现、被降权、被回滚。

**追问三：「社区实践里踩过什么坑，你们怎么看？」** 

两个有共识的坑我们都提前防了。一个是规模墙，纯靠索引文件导航，几百个页面就开始吃力，所以我们没有停在纯文本导航，直接内建了索引引擎和三路检索，这也是 Karpathy 原文自己预言的演进，他说维基大了就要上搜索引擎。另一个是状态漂移，有社区实践者总结出，会漂移的值不要写进正文，比如同步时间、行数、当前版本号，写进正文就会在正文里悄悄过期。我们的内容哈希在设计时就排除了时间戳这类易变字段，易变的不参与判断；历史事实走侧车的时间线正排记录，不和当前态混写。可以说社区的坑反过来验证了我们的设计决策。
