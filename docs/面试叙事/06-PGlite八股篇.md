## 30 秒开场介绍

PGlite 是 ElectricSQL 把完整的 Postgres 编译成 WebAssembly 的嵌入式版本，三兆左右，直接跑在进程里，不用起数据库服务、不用走网络。姿势上像 SQLite，但内核是货真价实的 Postgres，SQL、事务、GIN 索引、全文检索都是原生能力。存储形式就是一个标准的 Postgres 数据目录，在我们项目里落在仓库的 .dfmemory/pglite，被 gitignore 掉，定位是可丢的投影。对照我熟悉的 MySQL，核心差异三条：进程模型上是服务进程加网络对进程内函数调用；MVCC 上是 InnoDB 的 undo 版本链对 Postgres 的多版本堆加 VACUUM；索引上是 InnoDB 基本只有 B+ 树对 Postgres 的索引全家桶，我们重点用 GIN 做倒排支撑 BM25。单连接串行的模型和我们的单写者异步架构天然契合，数据目录坏了删掉从文件重建，这是内嵌库最放心的用法。

## 主线叙述（约三分钟）

**面试官：说说你们底层用的 PGlite，它是什么，怎么用的？**

先说为什么选它。我们的产品形态是单机本地部署，记忆库 git clone 下来就能直接用，不依赖远程服务。所以存储层必须是嵌入式的。PGlite 是 ElectricSQL 出品的一个嵌入式 Postgres：把完整的 Postgres 内核编译成 WebAssembly，三兆左右，直接跑在进程里。这里要强调它和 SQLite 的区别，SQLite 是一个独立的自研引擎，SQL 方言和能力都是自己的一套；PGlite 是货真价实的 Postgres，事务、多版本并发控制、GIN 倒排索引、全文检索、丰富数据类型，全是 Postgres 原生能力，只是运行形态从服务端变成了进程内库。

存储形式上，PGlite 没有任何私有格式，它维护的就是一个标准的 Postgres 数据目录。在我们项目里，这个目录落在仓库的 .dfmemory/pglite 下。目录里的结构和任何 Postgres 实例一样：存数据行的堆文件、预写日志 WAL、记录表结构元信息的系统目录。数据目录整体可拷贝，拷走就是一份备份；而且因为它是标准 Postgres 数据目录格式，理论上可以用真正的 Postgres 打开它，这就是升级路径。顺带说一句日志体系，和 MySQL 不一样，Postgres 没有 redo 加 binlog 两本账，只有 WAL 一本，崩溃恢复、复制、逻辑解码全从 WAL 来。我们的定位更进一步：这个目录被 gitignore 掉，它不是真相，是根据文件生成的投影，删掉之后一条命令就能从 markdown 文件全量重建。这是内嵌索引最放心的用法，持久化焦虑不存在。

对照我熟悉的 MySQL 讲差异，最值得讲三条。第一条是进程模型。MySQL 是客户端服务端架构，一个常驻服务进程，客户端走网络协议连接，3306 端口，服务端管连接池、管并发、管锁。PGlite 是进程内库，没有服务进程没有网络，查询就是一次函数调用，天然单用户。这不是缺陷而是形态选择，嵌入场景要的就是零部署零运维。

第二条是 MVCC 的实现，这是两家内核分歧最深的地方。InnoDB 的做法是，聚簇索引里每一行永远只存最新版本，旧版本放进 undo log，用回滚指针串成版本链，事务靠 Read View 沿着版本链找自己可见的版本，后台有 purge 线程清理不再被引用的 undo。Postgres 完全相反，更新一行就是在堆里写一个新版本，旧版本原样留在堆里，每一行带两个事务标记，创建它的事务号和使它过期的事务号，查询按快照直接判断堆里每一行对不对自己可见。所以 Postgres 回滚是瞬间完成的，把事务号标记一下就行，代价是死元组堆在表里，必须靠 VACUUM 清理；一个长事务会挡住清理，表就会膨胀。这是 Postgres 最经典的坑，InnoDB 把这个复杂度转移到了 undo log 上。

第三条是索引和全文检索。InnoDB 本质上只有 B+ 树一种索引结构，聚簇索引叶子就是行数据，二级索引回表；全文检索是 FULLTEXT 倒排，但能力弱，中文还要配 ngram 分词，相关性排序可控性差。Postgres 是索引全家桶，B 树、哈希、GiST、GIN、BRIN，其中 GIN 是广义倒排索引，本质是把词到行的映射做成索引，天然适合全文检索和多值列，还能建表达式索引，把一个函数的计算结果直接物化成索引。我们项目 BM25 这一路全部建立在 GIN 上，四条表达式索引建在物化的检索文本列上，命中走位图索引扫描，这个在检索篇里讲过。

特性怎么落到我们的用法上，四点。第一，事务。文档同步要把页面行、向量切块、图链接三张表在一个事务里写完，BEGIN 提交回滚，全靠原生事务，不会出现写一半的中间态。第二，建表和迁移。启动时跑幂等的建表语句，旧表结构不匹配就删掉重建，Postgres 的 DDL 是可以放进事务的，这是和 MySQL DDL 隐式提交很不一样的地方，迁移写起来干净。第三，向量存储。向量按二进制字节存，语义臂把向量字节加载到应用层算余弦，瘦查询只拉编号和向量字节，正文确定胜者后才取。第四，单写者契合。PGlite 同一时刻只处理一条命令，串行执行，这对我们的架构反而是优点：写路径默认进异步任务队列，队列本身就是串行的，单连接模型和单写者架构严丝合缝，不需要连接池。

边界和演进也想过。PGlite 什么时候不够用，三个信号：多进程多写者并发，需要真正的连接管理和行锁；数据量大到 WASM 内存和单目录扛不住；需要高可用复制备份。到那一步切换成本极低，配置里把引擎从 pglite 改成 postgres，配上数据库连接环境变量，两套引擎共用同一套建表语句和同一层业务代码，失败不回退。唯一的能力门槛是语义臂，在 postgres 引擎上会探测 pgvector 扩展，没有就跳过语义路并明确告警，字面路照常工作，宁可少一路信号不出错。

## 追问卡片

### 卡 1. PGlite 是什么？和 MySQL、SQLite 什么关系？

**追问一：「PGlite 是什么？」**

ElectricSQL 把完整的 Postgres 编译成 WebAssembly 做成的嵌入式数据库，三兆左右，跑在进程里。没有服务进程，没有网络协议，没有连接管理，查询就是一次函数调用。关键认知是它不是 Postgres 的仿制品或者子集，就是 Postgres 本身换了个运行形态，事务、多版本并发控制、各种索引、全文检索、扩展机制全是原生的。

**追问二：「和 MySQL 比是什么关系？」**

形态上是对立面，MySQL 是客户端服务端架构，常驻服务进程，客户端走网络协议连接，服务端管连接池、并发和锁，一个实例服务很多连接很多应用。PGlite 是进程内库，一个库一个进程独享，天然单用户。内核上更是两个流派，InnoDB 是 B+ 树加 undo 版本链的多版本实现，Postgres 是堆内多版本加 VACUUM 的实现，索引能力、全文检索、数据类型、DDL 事务性都有差异，后面展开。

**追问三：「它和 SQLite 是不是一类东西？」**

运行形态是一类，都是嵌入式、进程内、零部署、单文件或单目录。但内核完全不同。SQLite 是独立实现的自研引擎，类型系统宽松，功能是自己的一套方言；PGlite 是完整的 Postgres 编译产物，能力上限是真 Postgres。选型时这个区别是决定性的，我们需要 GIN 倒排、表达式索引、tsvector 全文检索、事务性 DDL，SQLite 给不了，Postgres 原生就有。等于用嵌入式的部署形态拿到了服务端数据库的能力。

### 卡 2. 存储形式是什么样的？

**追问一：「数据具体存在哪里，长什么样？」**

一个标准的 Postgres 数据目录。在我们项目里落在仓库的 .dfmemory/pglite 目录下。目录结构和任何 Postgres 实例一样：存数据行的堆文件、预写日志 WAL、存表结构元信息的系统目录。没有任何私有格式。在浏览器环境里它还能把数据目录放进 IndexedDB 或者私有的文件系统里，原理相同，载体不同。我们是命令行场景，就是本地磁盘目录。

**追问二：「这个目录的性质是什么？会进版本库吗？」**

不会，它被 gitignore 掉。这是刻意的定位：文件才是真相，markdown 记忆文件是权威数据，这个数据库目录只是根据文件生成的索引投影，可以随时删掉。删掉之后一条 rebuild 命令重新扫描文件、全量回填，索引就回来了。所以崩溃、损坏、升级失败，处置方式都一样，删目录重建，持久化焦虑不存在。

**追问三：「数据目录能迁移吗？」**

能，两个方向。横向，目录整体拷贝就是备份，或者迁移到另一台机器。纵向，因为它是标准 Postgres 数据目录格式，可以用真正的 Postgres 打开，配合官方的协议兼容工具还能用 psql 直接连进去查。这就是升级路径：单机用 PGlite，规模上来了把数据目录交给服务端 Postgres，或者直接切我们配置里的 postgres 引擎，schema 和业务代码完全不变。

### 卡 3. 对照 MySQL，事务和 MVCC 有什么不同？

**追问一：「MVCC 的实现有什么本质区别？」**

InnoDB 的路线是版本链外置：聚簇索引里每行永远只有最新版本，旧版本放 undo log，用回滚指针串成链，事务靠 Read View 沿链找可见版本，purge 线程后台清理。Postgres 的路线是版本堆内：更新一行就是在堆里写新版本，旧版本留在原地，每行带创建事务号和过期事务号两个标记，查询按快照直接判断可见性。后果各有代价：Postgres 回滚瞬间完成，但死元组占堆，必须靠 VACUUM 清理；InnoDB 堆里干净，但长事务会让 undo 膨胀。Postgres 最经典的坑就是长事务挡住 VACUUM 导致表膨胀。

**追问二：「那你们项目里表膨胀怎么办？」**

两层兜底。第一层，VACUUM 本身有，PGlite 内核带着自动清理，正常使用不会膨胀。第二层，也是我们真正的底气，索引是投影，膨胀到不可接受就删目录重建，几千个文档全量回填几分钟的事，数据零风险。这个后路是普通服务端数据库没有的，它们的数据是唯一真相，膨胀只能调参硬扛。

**追问三：「事务和 DDL 上还有什么差异？」**

两个点。一是 DDL 事务性，Postgres 的建表删表可以放进事务里回滚，MySQL 的 DDL 会隐式提交，事务直接断掉。我们启动时跑幂等建表、发现旧表结构不匹配就删掉重建，这种迁移操作在 Postgres 上写起来很干净。二是日志体系，MySQL 是 redo log 加 binlog 两本账，崩溃恢复用 redo，复制和归档用 binlog；Postgres 只有 WAL 一本账，恢复、流复制、逻辑解码全从它来，PGlite 的数据目录里那本 WAL 就是同一套机制。

### 卡 4. 对照 MySQL，索引和全文检索有什么不同？

**追问一：「索引能力的差异在哪？」**

InnoDB 本质只有 B+ 树一种，聚簇索引叶子就是行数据，二级索引叶子存主键回表，自适应哈希只是内部的加速优化，FULLTEXT 是特例的倒排。Postgres 是索引全家桶：B 树、哈希、GiST、GIN、BRIN，各自服务不同的访问模式。对我们最重要的是 GIN，广义倒排索引，把词到行的映射做成索引结构，天然适合全文检索这种一对多的匹配。

**追问二：「全文检索差异具体体现在哪？」**

MySQL 的 FULLTEXT 是一个功能点，中文要配 ngram 分词器，相关性排序算法可控性弱，基本只能拿来粗筛。Postgres 的全文检索是一套体系：文本预处理成向量格式，查询有专门的查询格式，打分函数现成，分词配置可定制，还能配合短语查询、权重标记。我们项目在这上面又叠了一层自己的东西：中英文双轨分词，中文用二元滑窗切分，四条 GIN 表达式索引建在物化的检索文本列上，命中走位图索引扫描。这套在 BM25 篇里详细讲过。

**追问三：「为什么坚持用数据库的倒排，不自己维护倒排？」**

倒排索引本身不难写，难的是生命周期：增量更新、崩溃恢复、和主数据的事务一致性。放进数据库里，这些全部是内核原生保证，倒排索引和文档行在同一个事务里更新，永远不会出现文档改了倒排还是旧的中间态。自己维护就要把事务、崩溃恢复、并发全部重做一遍，收益只是打分公式自由一点，不划算。

### 卡 5. 在你们项目里 PGlite 是怎么用的？

**追问一：「表结构大概什么样，怎么组织的？」**

核心几张表。每篇文档一行，存路径、标题、正文、内容哈希、状态，加上四个检索文本列；向量切块一张表，每块一行存文本和二进制向量；图链接一张表，存起点、终点、边类型；实体注册一张表。索引方面，检索文本列上建四条 GIN 表达式索引，普通过滤列建 B 树。全部建表语句是一份 SQL 文件，两套引擎共用。

**追问二：「事务边界怎么划的？」**

一条文档的同步是一个事务，页面行、向量切块、图链接三张表在同一个事务里写完，要么全进要么全回滚，不会出现文档进了、图链接没进的中间态。向量化是唯一例外，它单独一个事务，因为要调外部模型，失败了不能拖垮文档入库，只留空位事后补齐，这是写路径上的两阶段设计。整个索引删除重建也是分仓库进行的，多记忆库场景下清掉一个仓库的索引行不影响其他仓库。

**追问三：「单连接串行这个限制对你们是问题吗？」**

反而是契合。PGlite 同一时刻只处理一条命令，而我们的架构本来就是单写者：写路径默认进异步任务队列，队列串行消费，一次只有一条命令在跑；查询是命令行单进程场景，天然无并发。所以完全不需要连接池，也没有锁竞争问题。这个特性对服务端多连接场景是限制，对嵌入单用户场景是简化。

### 卡 6. PGlite 什么时候不够用？怎么演进？

**追问一：「什么信号说明该换引擎了？」**

三个信号。一是并发写，多个进程多个写者同时写，需要服务端数据库的连接管理和行级锁。二是规模，数据量大到 WASM 的内存上限和单目录体积扛不住，比如几十万篇文档加全量向量。三是运维需求，要高可用、复制、集中备份。我们的量级和形态下，这三个信号都还很远。

**追问二：「切换的成本是什么？」**

极低。配置里把引擎从 pglite 改成 postgres，配上数据库连接的环境变量，完事。两套引擎共用同一份建表语句、同一个业务抽象层，所有查询和写入代码无差别运行。切换是单向的，连不上数据库就报错，不静默回退到本地引擎，防止出现两边数据各写一半的分叉。

**追问三：「postgres 引擎上有什么能力差异？」**

一个门控点。语义向量这一路，在 postgres 引擎上会先探测 pgvector 扩展装没装，没装就跳过语义臂并明确告警，字面检索和图检索照常工作。设计原则是宁可少一路信号，不出一路假信号。我们的向量本来就一直按二进制字节存、余弦在应用层算，所以语义臂在两套引擎上的行为是一致的，pgvector 只是postgres 环境下的能力探测门槛，不是依赖。
